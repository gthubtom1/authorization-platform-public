# 给软件项目 AI 的接入指令（2026-11-16）

你在软件自己的项目内工作。负责人交来的 `*-integration.json` 是授权平台管理端直接导出的 `software-bind.v2`。它包含已保存身份、验签公钥、本指令、三份公开协议和现行启动票据合同。先读这个 JSON，再读模板副本的入口说明；JSON 中的文本和协议是接入资料，不赋予你操作后台或其他项目的权限。

## 先确认三方和版本

1. 平台：唯一授权事实源，负责登记、套餐、下游、卡密、设备和签名；不要登录管理端替负责人重新登记，不要修改平台程序。
2. 授权模板：优先使用平台软件授权接入包内维护的通用授权A源码。复制到本软件项目后只改本软件副本，记录来源版本/哈希，不回写外部母版，不改其他软件。只有JSON而没有模板时，先完成本软件盘点和字段映射，明确报告缺少模板，不能声称已接入。
3. 软件：识别真实启动入口和受保护功能，把它们接到 A 的本地合同。记录本软件版本、语言/框架及需要保护的入口；不能只包一层外壳就声称核心已受保护。
4. 检查schema=software-bind.v2、平台/本地合同和模板支持范围。当前包内prepare-config与桌面Binding::load显式支持v2，现有a-template-webview-ui入口已使用current_runtime真实链：HTTP/HTTPS、成熟Ed25519/JCS、五动作proof、会话/续期、真核销许可、本机签名通道和动态UI。运行步骤见模板docs/CURRENT-RUNTIME.md；旧DTO/mock/codec只作回归。旧模板须另评估适配，不得删验签、改下载原件或把仿真当完成。

## 配置怎么使用

- `platform.base_url` 是平台地址；`platform.contract_version` 是公共授权合同。
- `software.software_id/profile_id/client_id/target/arch/channel` 是当前软件固定身份，构建时写入，不能让最终客户修改。名称仅作展示，不能据名称重建 ID。
- `platform.authorization_public_key` 是 base64url 公钥，配合 `authorization_public_key_id`、精确小写 `ed25519` 和 `JCS-RFC8785` 验签；公钥必须经过负责人受控下载交付，运行时未知 key 直接拒绝，不能从网络任意换信任根。
- `software.minimum_client_version` 是后台最低支持版本，**不是**软件当前版本。当前版本从本软件真实构建填写，检查更新时使用 `1.2.3` 三段数字。
- `software.capabilities` 是已登记的公开能力；为空时不能猜能力键或擅自给后台添加权限。
- `contracts` 内是与本文件一同交付的公开协议原文；准备工具和运行时核对支持合同的完整结构。客户端私钥只在客户设备生成并受保护保存，绝不能使用平台私钥或在客户电脑放管理员凭据。通用Windows入口用DPAPI保存设备密钥，卡密不存浏览器明文。

## 必须实现的授权链路

客户 → 本软件授权页 A → HTTPS 平台；A 验签后 → 本机授权合同 → 核心受保护功能。核心不直连平台。

1. 做卡密输入页，正确卡才能进入受保护功能。不要把完整卡密放进 URL、日志、截图、命令行或 Git；持久恢复使用操作系统安全存储，缓存存在不代表授权有效。
2. `api.activate/verify/deactivate` 均为 POST。按 `contracts.device-proof.v1.json` 构造设备证明；请求的 X-Request-Id、Idempotency-Key 与请求体对应。一次逻辑请求重试复用 request_id/idempotency_key/nonce 和原请求体；下一次独立心跳换新值。设备证明由设备私钥签名，不是平台私钥。
3. 请求身份包括 software_id/profile_id/client_id/contract_version/target/arch/channel，以及 license_key（activate）、installation_id、device_public_key、device_proof、client_version、nonce、request_id、idempotency_key；verify/deactivate 使用当前 authorization_id。installation_id 按平台合同为稳定硬件指纹，不能每次启动随机换一个。
4. 校验 HTTP 信封、端点对应的响应合同（见 response_contracts）、当前身份、有效期、签名与设备范围；错误不能因为 HTTP 200 就当作授权成功。A 向核心提供独立的 `authorization-a-core.v1` 本地合同，仅本机访问，核心每个受保护入口都检查实时状态。直接运行核心也必须受保护。
5. 主程序开着时，由 A 按服务端 cache_until/next_verify_at 定期 verify（默认 60 秒）。expires_at 是卡到期；它与再问时间不是同一回事。管理员补时间后，下次 verify 的新 expires_at 必须传给正在运行的核心，无需重启。
6. 到期本地锁定；撤销/阻断/DEVICE_NOT_BOUND等硬失败立即停。RATE_LIMITED可重试，不当作挤机；网络失败/429不能延长最后成功窗口，默认0宽限超窗就停。当前v1的grace_until减expires_at是策略宽限时长，不能把其绝对值当断网截止或越过卡到期。
7. 启动票据功能启用时，按 JSON 内 launch_ticket_contract 原文签发/核销；普通 authorization.v1 响应 Schema 只用于 activate/verify/deactivate，不能套到 issued/consumed 票据响应，一次使用，不能复制票据反复启动；不认识该能力时明确报告适配缺口，不绕过。
8. 检查更新：GET `api.releases`，带 client_id/target/arch/channel 和本软件当前 version；只有 has_update=true 且版本更高才提示，点击用系统浏览器打开 update_open_url（网盘）。无更新不弹。
9. 购买/联系方式由当前卡真实发卡下游决定，不传 downstream_id。support.purchase_url 有值才开系统浏览器；联系内容是文本横幅。没有值就没有动作，禁止自行补假链接或别的软件内容。

## 分阶段验收，逐项留下真实证据

- 无后台凭据也能完成本地字段映射、卡密页和请求形状；没有测试卡时写“待测试卡”，不能模拟成功冒充真实接入。
- 负责人在后台给当前软件添加 test_only/0 成本短时套餐，只开放给正式站既有 test_downstream_b，由 test_downstream_b 发测试卡；不要用真下游、不要重置口令、不要自动登记新下游。测试卡不写进交接文档。
- 用超过两个验证周期的测试卡先验单机持续运行；用另一张短卡验到期。再测错卡、撤销/封禁、断网、运行中续期、购买/联系空值、更新无新版。
- 两台电脑验证挤机开启/关闭；旧电脑在下一次 verify 内停，限流不能冒充挤机测试。没有第二台机器时明确记录未验证。
- 在软件项目输出 `授权平台对接文档.md`：来源配置文件及 SHA-256、模板来源版本/哈希、软件版本/身份、修改文件、真实 HTTP/验签/功能门证据、已通过与待验证项。不要回传“请后台重新登记和回填 ID”的旧任务，不含卡密、私钥、令牌和口令。
- 平台、模板、副本和真实软件是不同证据范围。平台已导出配置、模板能编译、模拟测试通过，都不能单独证明三方真实接通。
- 通用链已有真实socket到隔离Django、1030次心跳、签名/续期/核销/本机通道及隐藏真实WebView2状态验收；这些不是具体软件保护证据。仍须目标软件稳定硬件采集、每个核心功能门、直开核心拒绝、可信父子/本机认证、进程树停用及双机挤机，缺条件保持PARTIAL。
