# 三层怎么接

准备顺序：后台创建并下载software-bind.v2 → JSON与平台维护的通用包复制到软件项目 → prepare-config准备 → 现有桌面入口消费配置 → 软件侧接稳定硬件和核心功能门。后台下载不自动修改软件；不再手填身份、请求重复登记。通用包已有真实HTTP/验签/会话/本机通道，具体核心仍要适配。

```text
中央授权平台（本仓库，网上的服务）
        │ 只有授权 A 用 HTTPS 调用
        │ /api/v1/public/licenses/activate
        │ /api/v1/public/licenses/verify
        │ /api/v1/public/licenses/deactivate
        │ launch-ticket / launch-ticket/consume（真实签发与核销）
        │ GET .../releases/（带当前版本号，看有没有新版）
        │ 以及配置 / 公告
        ▼
授权 A（每个软件一份：授权页 + Launcher + 缓存 + 本地桥）
        │ 只给自己的核心用
        │ 本机 127.0.0.1  /local/v1
        ▼
该软件的核心 EXE
```

## 为什么要三层

如果每个核心都直接打平台：平台地址、卡密字段、购买链接、更新逻辑会渗进每个 EXE。换一个软件就要改核心，还容易 A 软件的缓存给 B 软件用。

所以：

- **平台**只认登记过的 Profile，返回签过名的结果。
- **授权 A** 是这个软件的门面和翻译。
- **核心**只问自己的 A：「现在能不能用、有哪些能力」。

## 两套合同，不要混

| 合同 | 谁跟谁 | 版本名 |
|---|---|---|
| 公共授权 | A → 平台 | `authorization.v1` |
| 本地授权 | 核心 → A | `authorization-a-core.v1` |

版本对不上就停，不要「猜一下兼容」。

## 默认能力（大多数软件够用）

联网程序，卡密激活，绑设备，**主程序开着也要隔一段时间向平台验证**。只激活一次、本地用到卡到期，不够。可以配置：几台设备、换机次数、验证间隔、短暂断网宽限、最低版本、套餐天数、功能开关。

两套钟：卡到期用票里的 `expires_at` 本地关；挤机 / 解绑 / 撤销 / 阻断必须再调 `verify`，收到 `DEVICE_NOT_BOUND`（或撤销/阻断）才停。`cache_until` 不是核心到期。默认间隔 60 秒；已售卡下次 `verify` 跟现行间隔。平台 `verify` 硬失败不得被 `RATE_LIMITED` 盖住。

v1 **不做**：浮动席位、长期完全离线、支付、SSO。软件若需要这些，是以后另开合同，不是在 A 里偷偷加字段。
