# 授权 A 做什么

开工先读后台导出 software-bind.v2 内的 ai_handoff/contracts，再读模板副本入口。下面是运行时行为合同；身份从 JSON 映射，不再等待平台 AI 手工回填。

授权 A 是**这个软件自己的**一层，不是中央平台里的一个页面。每个软件一份副本，代码、缓存、测试都在那个软件的目录。

当前包内桌面入口已真实调用current_runtime：v2准备结果、HTTP/HTTPS、成熟Ed25519/JCS、五动作proof、心跳/续期、真核销后一次启动许可、本机签名接口与动态UI。旧DTO/mock/codec只保留回归。软件侧复用这条链，继续完成稳定硬件采集、具体核心功能门和真机验收；运行参数和边界见包内模板docs/CURRENT-RUNTIME.md。

## 必须做

1. 给最终客户一个授权页：输入卡密。购买和联系都跟**这张卡的发卡下游**走，禁止传 `downstream_id`。
   - 购买：`support.purchase_url` 有值时，点击用系统浏览器打开；没有则不显示可点入口，点了没有任何反应。
   - 联系：把 `support.qq` / `support.wechat` 做成横幅纯文本（给人看，不要当网址打开）。没有则不显示横幅，点了没有任何反应。
   - 更新：带当前版本号问 `releases/`；`has_update=true` 时点击打开 `update_open_url` 网盘。没有新版本则不弹窗、点了没有反应。
2. 用**写死在构建里的**身份去调平台，不要让用户改 `software_id`。
3. 激活 / 验证 / 解绑时带设备证明 `device_proof`（按平台规则签名），每个新的逻辑请求生成新的 `nonce`；结果未知重试必须复用原请求体和原请求标识。
4. 校验平台响应签名。签名不对、身份不对，当成失败，不要放行。
5. 用平台给的 `server_time` 判断到期，不要用客户电脑时钟放行。
6. 在本机 `127.0.0.1` 给核心提供 `/local/v1`。
7. 缓存按「这个软件 + Profile + 这张授权 + 这台设备 + 配置版本」隔离。缓存键不要用完整卡密。
8. 检查更新：带上当前版本号问平台；有新版再打开网盘。不要改平台 Nginx。

## 调平台时带什么（身份）

这些来自产品登记，不是页面输入：

```text
software_id
profile_id
client_id
contract_version = authorization.v1
target / arch / channel
```

客户只输入卡密。

## 三个常用动作

- 首次激活：`POST /api/v1/public/licenses/activate`
- 在线验证：`POST /api/v1/public/licenses/verify`
- 解绑当前设备：`POST /api/v1/public/licenses/deactivate`

### 检查更新（必须带版本号，不是只存一个网址）

每个软件当前对外只有**一个最新版本号**。历史版本仍留在平台里，方便撤回和对照。客户端自己做弹窗；平台只告诉「有没有比你更新的版本」。

1. **核对版本**：`GET /api/v1/public/software/{software_id}/profiles/{profile_id}/releases/`，参数必须带齐 `client_id`, `target`, `arch`, `channel`，以及客户端当前的 `version`。版本号必须是 `1.2.3` 这种三段数字。
2. **看响应**：`has_update=true` 且 `release.version` 比本地新，才弹出「有更新」。不要只看有没有网址。
3. **用户点下载**：优先打开 `update_open_url` / `external_download_url`（网盘，不吃 VPS 流量）。没有网盘、只有本站 `download_url` 时，用浏览器或程序去下这个包，**不要带卡密、不要把卡密写进网址**。没卡的人拿到安装包也打不开主程序。
4. 不要给整站 `/api/` 加跨域 `*`，也不要抄测试站上 GodSkin 当时的静态 updater。

### 换机、挤机与开着也要验证
- 主程序开着必须由启动器按 `cache_until` / `next_verify_at` 调用 `verify`。只 activate 一次、之后不再问平台，不算接上。
- **两套钟不准改混。** 卡到期：激活时写进票的 `expires_at`，启动器给主程序，主程序本地倒计时到点关。挤机 / 解绑 / 撤销 / 阻断：只改平台绑定事实，旧电脑必须再调 `POST /api/v1/public/licenses/verify`，收到 `DEVICE_NOT_BOUND`（或撤销/阻断）才关。
- **`expires_at` 会变，A 必须每次把最新值交给核心。** 平台管理员可以给客户补时间（续期）：只对已激活且未过期的授权生效，把 `expires_at` 推后并递增授权版本，不换卡、不用重新激活。A 在每次 `verify` 成功后要把新的 `expires_at` 推给核心，核心要接受倒计时变长。只在激活时取一次、之后不再更新的写法，会让补时间对已经开着的软件不生效。
- **不要把验证间隔写进核心到期倒计时。** 核心/标题栏仍用卡的 `expires_at`。`cache_until` / `next_verify_at` 只决定启动器何时再问，不是主程序能开多久。把再问间隔塞给核心当到期，单机也会自己关。
- 瞬时限流、暂时网络抖动在当前验证间隔内进行重试（2~3 次），不要直接关软件。重试必须串行等回包再发下一发，禁止多路并行重发同一套标识；收到409重放拒绝应按错误合同处理，不通过换标识绕过；结果未知时沿用原逻辑请求，状态已确定后下一次独立验证才生成新标识。但**默认禁止脱机常驻**：一旦断网、拔网线或持续失败超过当前验证间隔（默认 60 秒后），必须立刻通知核心强制关停主功能！
- **每次请求都必须带 `X-Request-Id`；`activate`、`verify`、`deactivate`三个POST都带 `Idempotency-Key`。**
  - `X-Request-Id`：你自己生成的唯一值（UUID 即可）。**重试时必须沿用同一个值。**
  - `Idempotency-Key`：值可以和 `X-Request-Id` 一样。
  - 新客户端统一在头和体提供一致的请求号及幂等键，不依赖兼容回退。头和体都缺请求号时返回MISSING_REQUIRED_FIELD；结果未知的重试复用原请求体、请求号、幂等键和nonce，下一次独立逻辑请求再生成新值。
  - 请求头名大小写不敏感；`Idempotency-Key` 与 body 里的 `idempotency_key` 同时出现时必须完全一致，否则返回 400。
- 平台对 `verify` 先判定再限流：已被挤掉或解绑后，即使该 IP 已触发限流，也必须返回 `DEVICE_NOT_BOUND`，不能先 429。`RATE_LIMITED` 只表示仍绑定、问太勤。
- 平台勾了「满员挤机」时，新电脑 activate 会成功，旧电脑绑定变成解绑。旧电脑下次 `verify` 会收到 `DEVICE_NOT_BOUND`（或同等「这台没有有效绑定」）。必须立刻停主程序。不要把它当成断网宽限。
- 没勾挤机、设备已满时，平台返回 **403 DEVICE_LIMIT_REACHED**，文案大意是：当前不允许新电脑挤掉旧电脑，请先在原电脑退出或联系代理重置。授权页要展示这句，不要只说“激活失败”。
- 客户在原电脑点击退出时，调用 `POST /api/v1/public/licenses/deactivate` 释放绑定，新电脑才能立刻激活。
- 断网宽限默认为0秒。当前v1的grace_until是expires_at加策略宽限的元数据，取二者差作为最后成功窗口的可配置宽限时长；不能拿grace_until绝对值作为断网截止，也不能延长卡到期。已被挤掉或到期必须停。
- 默认验证间隔 60 秒，约 1 分钟内看得见挤机。改当前策略后，已售卡下次 `verify` 也跟现行间隔。不要靠客户端 20 秒硬刷。
- 验收顺序：先单机开着超过验证间隔还在，再测两台挤机。

还要能拉配置和检查更新。完整字段表在 `docs/API-CONTRACT.md` 和 `docs/CLIENT-INTEGRATION-HANDOFF.md`，本夹不抄一遍。

## 不准做

- 不直连数据库，不带管理员账号，不带平台主密钥。
- 不提交 `downstream_id` 来挑联系方式。
- 不自己决定到期时间、额度、能不能激活。
- 不把 A 的缓存或本地端口借给别的软件。
- 不把这个软件的适配改动写回 A 母版，也不改别的软件的 A。
