# ADR-0004：版本化软件 Profile 与适配器隔离

- 状态：accepted
- 日期：2026-08-19
- 领域：软件接入、授权核心、跨软件隔离

## 决定

授权核心保持一套通用在线授权状态机。软件差异优先放入版本化 `SoftwareProfile`、`PolicyVersion` 和类型化 `CapabilityDefinition`；只有公共合同无法表达的真实特殊行为才新增隔离的 `SoftwareAdapter`，通过注册表按 `adapter_key + adapter_version` 选择。

每个客户端请求必须绑定 `software_id`、`profile_id`、`client_id`、`target`、`arch`、`channel` 和 `contract_version`。卡密生成时保存套餐/策略快照，激活实例保存 Profile、适配器和能力快照。跨软件、跨 Profile 的数据访问和状态改变必须由服务端根据关系和会话身份推导，不能信任客户端传入值。

## 原因

旧项目的真实接入已经暴露出“客户端字段、Profile、模块和版本容易漂移”的问题。按软件复制逻辑会让新软件污染旧软件；一张万能 JSON 表又会让数据库成为不可测试的隐式脚本。版本化声明 + 少量适配器可以让大多数新软件只登记配置，特殊软件的复杂性被限制在自己的边界内。

## 替代方案

- 每个软件复制一套服务和表：隔离清楚，但维护和迁移成本不可接受。
- 所有差异都塞入任意 JSON：短期快，长期无法校验、审计和兼容。
- 微服务：当前规模不需要，增加部署和跨服务一致性风险。

## 代价与回退

需要维护 Profile、策略、能力定义、适配器注册表和兼容测试；新增软件前置步骤略多，但可以避免每次改核心。若适配器机制证明复杂度超过收益，可保留 `generic-online-v1`，把未支持能力拒绝为 `ADAPTER_UNSUPPORTED`，不退回复制业务表。
