# ADR 0016: 卡密续期、版本归档与就地改版本号

- Status: accepted
- Date: 2026-09-18

## Context

产品负责人提出两件事：

1. **卡密续期。** 游戏更新后部分客户端用不了，需要给这些客户补时间。要求能多选、能按已激活未过期筛选、能选小时或天数批量加时间，客户下次握手就拿到新到期时间。
2. **版本记录膨胀。** 安装包一直放在自建 VPS 直链上，每次只替换文件、URL 不变。为让客户端弹出更新，每次都必须新增一个版本号，导致版本历史越堆越多，且已撤回的版本在页面上没有下一步，只能一直挂着。

这与既有决定冲突，需要书面改规则：

- 冻结前端下游页写着「续费会发新卡密，请在软件里激活新卡」。
- `scripts/release_candidate_acceptance.py` 有硬门禁：冻结页出现 `>续期<`、`>延期<` 或 `/licenses/.../extend|renew/` 即判候选失败（`expiry-grows-renew-or-extend`）。
- `docs/DOMAIN-RULES.md` 的版本规则只允许撤回、改网盘地址、删除已撤回的安装包文件；版本行不可归档、版本号不可修改。

## Decision

### 一、卡密续期

1. **只有已激活且未过期的授权可以续期。** 判断依据是服务端时间：`LicenseInstance.state ∈ {active, grace}` 且 `server_now < expires_at`，同时卡密状态是 `activated`。未激活卡不扣天数，因此不在续期范围内；已过期、已撤销、已阻断、已回收、已归档、墓碑卡一律拒绝。
2. **续期改的是服务端到期事实，不是套餐。** 服务动作同时更新 `LicenseInstance.expires_at` 与 `LicenseCard.expires_at`，并把 `authorization_revision` 加 1，使客户端下次 `verify` 必然拿到新的 `expires_at`，不会被 `not_modified` 跳过。套餐快照、`duration_seconds`、设备规则、下游归属、`quota_cost` 都不改。
3. **续期不产生额度流水，不计收入。** 收入口径仍是「已激活卡发卡时锁定的套餐额度成本」。续期是运营方赠送的时间，不写账本、不写流水、不改 `quota_cost`。
4. **两套钟不变。** `cache_until` / `next_verify_at` 仍由服务端按 `min(expires_at, server_time + verify_interval_seconds)` 计算。续期只把 `expires_at` 推后，不得把验证间隔写进核心到期。
5. **批量必须预览后确认。** 预览按当前筛选返回冻结的 `authorization_ids` 列表、张数和每条的新到期时间；确认只接受这批 ID，禁止在确认阶段按筛选条件重新活查。逐条独立事务，允许可追踪的部分失败并逐条汇报。
6. **单位只接受小时和天。** 1 小时 = 3600 秒，1 天 = 86400 秒，与套餐同一口径。单次上限 366 天；续期后的到期时间不能超过这张卡激活起 10 年（防手滑连点，不是运营限制），超出返回 `RENEWAL_LIMIT_EXCEEDED`。
7. **幂等与审计。** 一次续期请求一个 `Idempotency-Key`，同键重放返回同一结果且不重复加时间，同键不同内容返回 `IDEMPOTENCY_CONFLICT`。每次续期写不可变操作记录与审计，含每条的前后 `expires_at`、增加秒数、原因和操作者。
8. **不做减时间。** 不提供缩短到期时间的入口；改错用再补或撤销处理。

### 二、版本归档

9. **新增 `archived` 版本状态。** `published` 或 `withdrawn` 的版本都可以归档，**不必先撤回**。归档从版本表默认列表消失，但仍占用版本号、仍可追溯、仍保留操作记录。归档已发布版本时，该版本同时失去公共可见性（registry 回退到剩余已发布里版本最高者），确认框必须写明这一点。

### 三、就地改版本号

10. **允许修改已发布版本的版本号。** 用于「同一个网盘地址、只替换文件」的场景：把当前分发中的版本号从 `2.0.8` 改成 `2.0.9`，客户端立即收到更新提示，且不新增版本行。已撤回版本只做归档，不改号（改完客户端也看不到，容易误以为更新已生效）。
11. **改号约束：** 新版本号必须符合三段数字格式；同一软件、Profile、平台、架构、通道下不得与另一条未丢弃版本冲突；新号必须大于该通道下其他所有已发布版本的版本号（即改号等于把这个版本提到最新）；草稿不改号（丢弃重发即可）。改号同时更新 Manifest 里的 `version`，写审计前后值和操作记录。

## Alternatives

- **续费=再发一张新卡（原方案）**：客户要自己再激活一次，每次多一张卡密、多一次额度成本，运营方无法批量补时间。否决。
- **允许给已过期卡拉回有效期**：需要把卡密状态从 `expired` 拉回 `activated`、绑定状态从 `expired` 拉回 `active`，等于做一套「过期复活」语义，且过期卡对客户已经无用。否决。
- **续期写额度流水**：会把赠送时间伪装成销售，污染收入口径。否决。
- **物理删除版本行**：`ReleaseOperation` 不可变记录、`previous_release` 自引用链、撤回回退和审计都依赖这些行。否决。
- **释放被归档版本的版本号**：会让同一版本号对应两份不同内容，客户端比较会错乱。否决，归档仍占号。

## Consequences

- 冻结前端可以出现「续期」入口；`release_candidate_acceptance.py` 的续期门禁改为「续期不得针对未激活或已过期授权」。
- 冻结页版本表新增「归档」与「改版本号」操作，版本号不再是不可变事实，但审计保留前后值。
- 版本表默认视图变短，需要「已归档」筛选才能看到历史。
- 续期是运营动作，不是财务动作：账本、收入、套餐快照都不动。

## Validation And Rollback

- 续期：定向测试锁住「未激活卡续期被拒」「已过期授权续期被拒」「已撤销/已阻断续期被拒」「续期后 revision 递增且 verify 返回新 expires_at」「同键重放不重复加时间」「批量确认只认预览冻结的 ID」「不产生额度流水」「部分失败逐条汇报」。
- 版本归档：锁住「已撤回版本可直接归档」「已发布版本未撤回不能归档」「归档后默认列表不出现、按状态筛选可读回」「归档后版本号仍占用」。
- 改号：锁住「格式校验」「撞号拒绝」「改小拒绝」「草稿改号拒绝」「Manifest 与记录同步」「审计含前后值」。
- 回滚：两项都是加法。归档可以恢复为归档前状态（`archived_from_status`）；改号可用审计里的前值改回。续期不做自动回滚，需要时按撤销处理。
