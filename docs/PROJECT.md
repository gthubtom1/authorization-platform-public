# 授权系统项目定义

## Outcome

交付一个可以由 AI 持续开发和验证的通用授权平台：管理员管理多个软件和下游，下游使用额度生成授权卡密，最终客户通过对应软件自己的授权 A 页面/Launcher 激活，中央平台统一判断授权并留下完整审计链。

平台自身是部署在 VPS 上的 Web 应用，管理员和下游通过浏览器访问两个独立角色入口；它不是桌面 EXE。授权 A、核心 EXE 属于平台外部的客户端接入层，不改变管理端和下游端的 Web 入口边界。

## 当前 Web 页面入口合同

当前冻结的本地静态前端以 `http://127.0.0.1:8123/` 为基址，页面后缀区分入口和状态。以下是 8123 页面合同，不是 Django URL 合同：

- 根路径 `GET /` 以及 `/./`、`/.`、`/%2e/`、`/%5c/` 等根等价路径永远返回 HTTP `404`，不能自动打开、跳转、目录列出或代理到 `entry.html`；分流/入口页面不能从域名根路径泄漏。需要入口时只能使用明确的受控路径，并在目标 Nginx 验收中单独核对根路径 `404`。
- 管理端工作台：`http://127.0.0.1:8123/manage.html`
- 管理端未登录：`http://127.0.0.1:8123/manage-login.html`
- 下游工作台：`http://127.0.0.1:8123/downstream.html`
- 下游未登录：`http://127.0.0.1:8123/downstream-login.html`
- 下游未注册：`http://127.0.0.1:8123/downstream-register.html`
- 隐藏分流页 `entry.html` 只能手输受控路径打开；管理端/下游工作台、登录页和 `preview.js` 都不得链到它。域名根路径以及根等价路径仍然 404。

部署时，将 `http://127.0.0.1:8123/` 替换为正式域名，页面后缀保持用于区分不同页面。根路径是基址占位，不应被解释成另一个管理端页面，也不应据此创建 8143 替代入口。

## 用户

- 管理员：平台所有者，配置软件、套餐、下游、额度、授权、设备、版本和风控。
- 下游：渠道商，只能管理自己被开放的软件和自己的卡密、设备、额度、渠道信息。
- 最终客户：不直接登录平台，只在软件客户端输入卡密并完成设备绑定。

## 新软件接入

管理员主要填写名称，后台生成稳定身份并预填规则；套餐可稍后添加。对应软件行下载 software-bind.v2，放入软件项目并使用授权模板副本。JSON 自带三份公共协议和软件侧 AI 指令，不带卡或管理凭据。三方验收与操作顺序统一在 `接入说明/00-先读我.md`，不再默认通过 AI 登录后台登记回填。

软件下架后可由管理员重新上架，但不自动恢复下架时关闭的下游经营范围；必须明确重新开放。参数已保存后列表读取失败应提示已保存，未知结果重试复用原提交。实现/上线状态以STATUS为准。

## 核心产品逻辑

```text
软件 → 下游软件关系 → 套餐 → 授权卡密 → 授权实例 → 设备绑定 → 到期/撤销

额度兑换码（发行时不绑定下游） → 任一活跃下游一次性兑换 → 该下游额度账户
下游额度账户 → 生成授权卡密扣款 → 未激活卡回收 → 原额返还
```

中央平台是授权事实源。核心 EXE 不直接连接中央平台，也不保存平台密钥；它只通过本软件专属的授权 A 获取短期、类型化的本地授权结果。授权 A 代表核心 EXE 调用中央平台，不能自行决定有效期、下游归属或授权结果。

## 现行方案（2026-09-13 以后）

- **更新：** 每个软件当前一个对外版本号，必须是 `1.2.3`。客户端带版本问平台，有新版打开网盘。本站 ZIP 可上传、谁都能下，不是默认渠道。
- **备份：** 整份数据库 `.enc`（含卡密状态、额度流水、设备绑定、发版网盘地址）。不含安装包。异地副本只有 GitHub。**告警**用 Telegram 机器人（2026-09-27 定的口径），但 Telegram 只发失败通知，备份数据本身不放那里。
- **接软件：** 在软件项目中修改授权A副本和核心功能门。平台缺陷由本仓库处理；软件接入只改软件项目，不改运行Nginx。
- **不做：** 多级代理、为测试复制一套软件身份（测试用途通过受控test_only套餐及隔离环境表达）、跨域 `*`、网址带卡密、R2/坚果云备份。

## 三层产品边界

```text
中央授权平台
  多软件 / 多下游 / 卡密 / 授权 / 更新 / 公告 / 联系方式
                    │ HTTPS（仅由授权 A 调用）
                    ▼
授权 A（每个软件一套）
  授权页 / Launcher / 平台 API 客户端 / 本地缓存 / 本地桥接 API
                    │ 本机稳定合同（默认 127.0.0.1 loopback）
                    ▼
核心 EXE
  业务功能 / 产品 UI / 受保护功能门；不直连中央平台
```

每个软件的授权 A 独立维护、独立版本化、独立缓存和独立回归。新增软件只增加自己的授权 A、Profile、能力和产品档案，不把软件专属分支堆进中央平台或其他软件的核心 EXE。

## 授权 A 母版、副本与三方适配顺序

授权 A 的通用母版是独立的客户端接入模板，不是中央平台的页面分支，也不是某个核心 EXE 的专属代码。接入不同软件时，先把母版复制到该软件自己的客户端/核心项目目录，复制后的授权 A 作为独立副本维护、独立版本化和独立回归；适配某个软件只能修改该副本，不能回写或覆盖母版。

每个副本都必须记录来源母版版本/哈希、平台公共合同版本、目标软件的 `software_id`/`profile_id`、授权 A 到核心的本地合同版本和自己的测试证据。母版后续更新必须通过明确的版本同步和冲突审查进入副本，不能因为某个软件接入而自动改动其他副本。

平台公共服务已部署。每款软件按“后台创建→下载JSON→复制模板→适配A与核心→实际验收”推进，不重复启动整个平台首次建设。平台功能缺陷回本项目处理，软件侧在自己的软件项目修改A副本及核心功能门，不回写模板母版或其他软件；具体任务状态见STATUS。

## v1.0 必须支持

- 多软件和下游软件关系
- 软件套餐及套餐快照
- 不预绑下游、未兑换前无期限的一次性额度兑换码，以及不可变额度流水
- 仅下游本人生成授权卡密；管理员不代发，但有全平台卡密总表可查询和回收未激活卡
- 未激活卡回收并返还原始额度
- 管理员额度回收和强制撤销授权
- 在线激活、验证、设备绑定、解绑和换机规则
- 基础风控、审计、渠道支持和客户端配置
- 每个接入软件独立的授权 A，以及授权 A 到核心 EXE 的版本化本地合同

## v1.0 明确不做

- 多级代理和卡密跨下游转移
- 最终客户平台账号
- 平台最终销售价格和平台发卡网
- 自动支付、退款和完整订单中心
- 完整空网离线授权、SSO、多管理员审批
- 微服务、Kubernetes、高级实时风控和复杂灰度发布
- 中央平台直接连接或控制任何核心 EXE；核心 EXE 直接调用中央平台 API

## 通用接入边界

平台的“通用”指：符合在线、服务端判定、卡密激活、设备绑定和短期验证模型的软件，可以由自己的授权 A 通过同一份 `authorization.v1` 合同接入，不因语言、桌面框架或 UI 类型不同而复制一套中央平台。这里的“客户端接入”默认指授权 A，不是核心 EXE 直接接入。

软件差异通过 `SoftwareProfile`、版本化授权策略、类型化能力定义、软件专属授权 A 和必要时的隔离平台适配器表达。新软件默认走 `generic-online-v1`；浮动席位、长期离线、SSO、支付和复杂企业审批不偷偷塞入 v1，而是进入独立扩展评审。

文档只负责定下产品契约，数据库约束、服务层、两段 API Schema、授权 A 的本地桥接测试、跨软件回归、审计和 Feature Guard 负责证明“新增软件不影响旧软件”。

产品接入只针对用户拥有或明确获准修改、再发行的软件。对没有授权的第三方软件，不进行破解、绕过授权或隐蔽替换；发现权限不清时先暂停接入。

## 已确认的零基础操作原则

- 功能必须完整，但页面必须简单：一个页面一个主要任务，默认只展示完成当前任务所需的字段；高级配置、筛选和历史按需展开，不用页面数量或控件数量冒充完整性。
- 本地先改、测试、真实验收和创建检查点，VPS 只接收本地已验证的固定版本。
- 下游账号最小身份是用户名和密码；管理员直建不需要邀请码、标识或显示名称。
- 邀请码独立生成，发行时不绑定下游且未使用前无期限；每枚只在注册成功时消费，失败注册不落库、不消费。页面只按单码管理，不展示批次。
- 额度兑换码发行时不绑定下游且未兑换前无期限；任一活跃下游可兑换一次，额度进入实际兑换者的唯一额度账户。页面只按单码管理。
- 只有下游能为自己生成授权卡密；管理员不代发、不绕过额度出卡。管理员有全平台单卡总表，可查询、搜索完整码、显示完整码，并勾选或按筛选回收未激活卡（额度退回原下游账本）。
- 活跃对象先归档；归档停止权限但保留列表；归档对象才允许彻底删除。套餐删除后从目录消失，该套餐现存卡密全部失效（未激活作废并退回额度，已激活撤销），快照、流水和审计留下。已过期/已撤销/已回收满 30 天的卡密可批量归档后删除。审计和额度流水不删除。管理端可清理上传包、临时导出和日志残留，防止磁盘涨满。
- 管理员可设置额度卡购买链接；下游登录、注册和登录后页面显示该链接，随保存变化。
- 下游按软件自定义购买链接和客户支持，只出现在用该下游卡密激活的授权 A 页面。
- 管理端和下游端展示今日、本月、累计收入：只计已激活卡密的套餐额度成本，未激活不计；0 成本测试卡激活后仍是 0；单位是额度，不是人民币。管理端累计等于各下游累计之和，下游只看自己发出并已激活的卡。
- 卡密、邀请码和额度兑换码可在授权范围内重复查看、复制或下载；完整码显示/复制/下载不写“谁看过”审计。生成、兑换、作废、回收、撤销仍写审计。密码只能重置，不能回显。
- 公告不作为主流程。更新必须带 `1.2.3` 版本号；默认填网盘地址，客户端问 `has_update` 再打开网盘。本站上传包是备用。
- 验收必须按真人和攻击者视角走完整链路，同时核对页面、接口、持久化和审计/余额/状态。

## 默认业务规则

- 首次激活必须在线；断网宽限期可按软件配置。
- 邀请码、额度兑换码和授权卡密在未消费、未兑换或未激活前均无到期时间，但管理员可以明确撤销；三类码都只能成功使用一次。
- 授权卡密第一次成功激活时才按套餐快照计算授权到期时间；卡密激活后不能再次创建第二个授权实例，回收后的卡密不可恢复。
- 套餐属于具体软件，不存在全平台统一价目。以后每新增一个软件，都在该软件下自定义卡种名称、有效期、设备数和单卡额度成本；改 A 软件价格不影响 B 软件。发卡先选软件，再选该软件自己的套餐。套餐额度、有效期和授权规则在生成卡密时保存快照。
- 套餐有效期以正整数秒保存，管理端可用分钟、小时、天录入；允许创建 `test_only` 的 1 分钟（60 秒）测试卡，用来验证客户端到期锁定。
- 授权到期和验证统一使用服务端 UTC 时间；后台、报表和统计默认按北京时间（`Asia/Shanghai`）显示，VPS 系统时区不能改变业务结果；客户端修改本机时间不能绕过有效期。
- 一张卡密的授权实例和设备绑定历史独立保存，不能用单一“激活设备”字段代替。
- 额度只能通过流水改变；余额是可重建的汇总，不是唯一事实源。
- 下游暂停/关闭后不能开展新业务；已有客户授权是否继续有效按软件策略决定并记录。
- 下游联系方式、购买链接、公告和更新元数据由中央平台按真实卡密归属解析；授权 A 缓存后传给核心 EXE，核心不自行拼接或猜测下游身份。

## 成功标准

逐软件产品终态（含授权A，需要在该软件项目验证）：管理员和下游可以在本地演示完成一条完整链路：创建软件和套餐 → 开放下游 → 充值额度 → 下游生成卡密 → 管理员在总表中能查到这些单卡 → 通过对应授权 A 激活 → 授权 A 把结果交给核心 EXE → 查询设备 → 回收未激活卡 → 额度返还 → 管理员撤销授权 → 查询审计记录。

G-001中央平台基线（首次建设范围已完成并部署，当前验证边界见STATUS）：同一条链路做到「管理端/下游真实网站 + 平台激活 API」，**不含**授权 A 页面、核心 EXE 和 LocalBroker。完成判据见 `docs/STATUS.md`。
