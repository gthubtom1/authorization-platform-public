# 领域规则与数据契约

## 新软件接入简化（2026-11-16）

新建默认只要求名称，软件 ID 由服务端在持久幂等事务内生成；Profile/客户端身份与生效策略一次保存。允许暂不建套餐（无套餐不能发卡，不合成零成本正式套餐），也不自动开放下游。设备 1、60 秒验证、0 断网宽限、允许挤机和每日换机 5 为创建默认，仍允许在既有规则范围内修改。单软件下载 `software-bind.v2` 是只读交付，不能改变卡密、额度、设备、授权实例、密钥或客户端接通状态。业务和兼容边界见 API 合同“新软件自助接入”。

本文是实现前的业务规则基线。若页面需求与本文冲突，先更新本文或新增 ADR，再写代码。

## 领域词汇

- 软件（Software）：平台管理的一个独立授权产品。
- 下游（Downstream）：被管理员授权经营某些软件的渠道商。
- 套餐（Plan）：某个软件的一组授权规则，包括有效期和额度成本。
- 额度（Credit）：下游用于生成授权卡密的整数单位，不等同于人民币。
- 额度卡（Quota Card）：一次性兑换为下游额度的凭证。
- 授权卡密（License Card）：最终客户用于激活软件授权的凭证。
- 授权实例（License Instance）：一张授权卡实际生效后的授权记录。
- 设备绑定（Device Binding）：授权实例与设备的关系及其历史。
- 软件 Profile（Software Profile）：同一软件的一个客户端身份、目标平台、通道和协议版本。
- 授权策略版本（Policy Version）：在某一时间生效的不可变授权策略快照。
- 能力定义（Capability Definition）：软件可声明的、带类型和范围的功能或额度参数。
- 软件适配器（Software Adapter）：仅处理真正产品特有映射的隔离代码模块，不负责通用授权事实。
- 授权 A（Authorization A）：某个软件专属的授权页、Launcher、中央平台 API 客户端、本地缓存和 LocalBroker；它把中央平台结果交给自己的核心 EXE。
- 启动票据（Launch Ticket）：一次启动换一张的短期单设备绑定票据。覆盖层只钉平台公钥，凭票拉起；过期、核销、设备对不上即失效。行保留作审计，不物理删除。
- 本地授权合同（Local Contract）：授权 A 与同一软件核心 EXE 之间的版本化 `/local/v1` JSON/IPC 合同；它不是中央平台 API 的替代事实源。

## 归属与所有权

授权卡密至少要区分以下字段：

- `software_id`：卡密属于哪个软件。
- `plan_snapshot_id`：生成卡密时使用的套餐快照。
- `original_downstream_public_id`：最初由哪个下游生成或分配的公开 ID。
- `current_downstream_public_id`：当前可操作和可回收的下游公开 ID。
- `created_by`：实际创建者及角色。
- `source`：下游生成或其他受控内部来源；“管理员创建”不是 v1 授权卡密发行语义。
- `batch_id`：内部事务/幂等分组引用；不作为用户可见批次、筛选字段或回收范围。
- `quota_cost`：生成时实际扣除的整数额度。

v1.0 不开放卡密跨下游转移，但保留原始归属和当前归属的分离，避免未来推翻数据结构。

## 核心对象

### Software

必备信息：名称、稳定 ID、描述、图标、状态、当前版本、授权策略、客户端配置。

授权策略至少包含：最大设备数、是否允许换机、每个北京自然日换机次数、设备证明策略、验证间隔、断网宽限期。正式、测试、本地新建软件的默认验证间隔是 60 秒。`cache_until` / `next_verify_at` 读 Profile 当前 ACTIVE 策略的验证间隔，已售已激活卡也跟着变；实例上的策略快照不改。最大设备数、断网宽限、设备证明仍锁发卡快照。禁止按软件名写死间隔。

一个 Software 可以有多个 `SoftwareProfile`，每个 Profile 至少保存 `profile_id`、`client_id`、`contract_version`、`target`、`arch`、`channel`、`adapter_key`、`adapter_version` 和状态。Profile 是客户端接入隔离边界，不能用一个全局“当前客户端”字段替代。

默认适配器为 `generic-online-v1`。产品专属差异优先登记为类型化能力定义和策略配置；只有公共合同无法表达时，才使用注册表中的版本化适配器。数据库不得存放可执行脚本，核心服务不得按软件名堆积分支。

### Downstream

必备信息：用户名、密码哈希、状态、注册时间、最后登录时间。显示名称、联系方式和渠道配置不是下游账号成立的前置条件；管理员直建只填写用户名和密码，邀请码注册由下游自行填写用户名和密码。

状态：`active`、`suspended`、`closed`。邀请码是独立对象；注册失败不创建 `invited` 下游记录，注册成功后直接创建 `active` 账号。

下游状态只决定下游能否登录和发起新业务。已有客户授权默认继续到期，安全事件可以通过单独撤销授权立即终止。

认证凭据使用 Django 内置 User 的密码哈希和会话；业务侧另建 `DownstreamProfile`，至少保存不可变的 UUID `public_id`、User 关系、状态、注册时间、最后成功登录时间、关闭时间和关闭原因。下游展示名、联系方式和邀请码不是账号成立的前置条件。所有下游查询必须从当前会话得到 Profile，不能信任表单或 URL 中的 `downstream_id`。

注册用户名在服务层统一去除首尾空格并转换为小写后校验；重复用户名、无效密码和其他注册失败不能创建 User/Profile，也不能消费邀请码。管理员直建与邀请码注册最终都创建同样的 `active` DownstreamProfile。

`closed` 是归档态：禁止登录和新业务，但保留列表和关联历史。只有已归档对象才允许进入删除服务；删除必须先写最小脱敏墓碑，再删除凭据和 Profile，不能通过 Django Admin 或直接 ORM 绕过归档门槛。

### DownstreamAdminOperation

管理员创建、暂停/恢复、归档和删除下游的 API 写操作都必须带 `Idempotency-Key`。`DownstreamAdminOperation` 以 `(actor, idempotency_key)` 唯一保存动作、目标下游公开 ID、目标用户名摘要、服务端 HMAC 请求摘要、脱敏响应、原始 HTTP 状态和时间；请求哈希可以覆盖初始密码，但密码原文不进入数据库、日志、审计或响应。相同管理员、相同键和相同请求只重放原响应；同键换动作、目标或请求内容返回 `IDEMPOTENCY_CONFLICT`；操作记录模型层拒绝普通更新、批量更新和删除。

业务状态变化和幂等记录必须在同一事务提交。失败或进程中断只能整体回滚，不能留下“账号已创建但没有可重放结果”或“操作记录已成功但账号未改变”的半成品。删除后的操作记录仍保留目标公开 ID、用户名摘要和脱敏响应引用。

### PasswordOperation

密码操作是独立的不可变操作事实，不保存当前密码、新密码或确认密码。每条记录保存操作者、目标 User 的可空引用、目标下游 `public_id` 快照、目标用户名摘要、动作（`change`/`reset`）、操作者作用域内的 `Idempotency-Key`、使用服务端密钥生成的请求 HMAC、可重放的脱敏响应和创建时间。User/Profile 删除后，操作记录仍保留最小目标引用；普通 ORM 更新、批量更新和删除必须被模型层拒绝。

管理员或 active 下游只能修改自己的密码；管理员重置只能作用于指定且未归档的下游。新密码仍走 Django `set_password()` 与 `validate_password()`，不得与当前密码相同；当前密码错误、确认不一致、强度不足、对象不可用和幂等冲突都不得改变账号密码或 `session_version`。成功自助修改保留当前会话，其他旧会话由 Django 密码摘要失效；下游自助修改和管理员重置还必须递增目标 `DownstreamProfile.session_version`。

成功、失败和限速都写 `auth.password_change` 或 `auth.password_reset` 审计。审计只允许目标用户名摘要、目标 Profile、操作 ID、幂等键摘要、原因长度/摘要、稳定错误码和前后会话版本等脱敏元数据；密码、确认密码、原因原文和完整请求体不进入审计、日志、响应或 URL。

### InvitationBatch / InvitationCode

邀请码在页面上只按单码管理，不展示批次。后台若保留内部生成分组，仅用于事务与幂等，不得出现在界面。邀请码发行时不绑定任何下游，未使用前不设置业务到期时间；每枚至少保存创建者、随机值哈希、必要时的加密密文、状态、创建时间、消费时间、消费 Profile、消费用户名摘要和撤销原因。

邀请码状态：`issued`、`consumed`、`revoked`、`expired`、`archived`。新生成的 `issued` 一直可用，直到注册成功或管理员撤销；失败注册、错误密码和临时限流都不能消费或过期新码。历史数据中因旧 TTL 已到期且从未使用的码按 `effective_status=expired` 处理，可直接归档；仍处于有效 `issued` 的码必须先撤销。归档后进入归档分类，不能注册或再次使用；删除只接受已归档记录。

完整邀请码不进入日志。仅管理员可以通过完整码精确查找、按需显示、复制或下载；**不**写入“谁看过”审计。生成、撤销、注册成功/失败仍写审计。撤销未使用单码不可恢复。

注册消费必须在一个数据库事务内完成：锁定邀请码 → 校验状态 → 创建 User → 创建 DownstreamProfile → 加入下游角色组 → 将邀请码标记为 `consumed`。任一步失败都不得留下账号或消费结果；同一邀请码并发注册只能成功一次。

### DownstreamSoftware

记录下游是否可以经营某个软件，以及开放时间、关闭时间、允许使用的套餐范围和备注。

所有下游生成卡密的请求都必须由服务端重新检查这条关系。unused 卡密首次激活也必须存在该下游对该软件 `status=ACTIVE` 的行；无行与 `CLOSED` 都拒绝。已开通授权的 verify 继续。回收 unused 卡密不查经营范围。

### Profile、下游配置、授权实例覆盖与授权 A 缓存

配置不是独立的万能表，而是挂在已有授权归属对象上的三层产品中立数据：

| 层级 | 实际持久化位置 | 作用和版本 |
|---|---|---|
| Profile 默认 | `SoftwareProfile.support_purchase_url`、`support_qq`、`support_wechat`、`announcement_enabled`、`announcement_title`、`announcement_body` | 公告等仍可作软件默认；**不得**当作客户端渠道通知（购买 URL / 联系方式）的候选 |
| 下游软件配置 | `DownstreamSoftware.configuration_enabled` 及同名支持/公告字段 | 某个下游在下游页给自己发出的卡密填的渠道通知：购买额度卡网站 URL + 一段联系方式文本（邮箱/手机/微信等均可）。没填就是空。设置或清除都生成新的 `DownstreamSoftware.config_version` |
| 授权实例覆盖 | `LicenseInstance.configuration_override`（完整的已规范化字段对象） | 某个授权实例的客户级覆盖；设置生成新的 `LicenseInstance.config_version`，不改变授权期限、设备规则、卡密或下游归属 |

配置字段的规范化键固定为 `purchase_url`、`qq`、`wechat`、`announcement_enabled`、`announcement_title` 和 `announcement_body`。数据库字段使用 `support_` 前缀只是存储命名；对外响应使用稳定的 `support`、`announcement` 和 `modules` 结构。

每次设置配置都会先规范化。Profile 与下游软件配置的更新只覆盖请求里出现的键：缺省键保持该层当前库值，不回填更低层，也不把缺省键当成空串；请求里显式空串仍清空该字段。下游 `clear=true` 关闭整层并清空该层字段。授权实例覆盖仍是整份对象替换：未提交的键使用该层空值/关闭默认，不从较低层逐字段合并。授权实例清除在数据库中保存为空对象 `{}`，运行时把空对象视为“没有覆盖”。

服务端解析配置时必须使用授权实例保存的真实 `current_downstream_public_id` 和 `software_id`，不能信任授权 A、核心 EXE 或页面提交的下游 ID。

**渠道通知（`support.purchase_url` / `qq` / `wechat`）**只跟这张卡密当前归属下游在下游页保存的内容：该下游 `configuration_enabled=true` 时用它填的购买 URL 和联系方式文本；没保存过或字段为空就给客户端空（`support` 三个键都空时整段 `null`，页面隐藏，不要用「无」当字段值，也不要用 Profile 或另一字段顶上）。授权实例覆盖非空时仍可改这一张卡。

**公告**仍按完整配置层回退：

```text
LicenseInstance.configuration_override（非空时）
  → DownstreamSoftware（configuration_enabled=true 时）
  → SoftwareProfile
```

清除下游配置会关闭 `configuration_enabled`、清空该层字段；渠道通知回到空，公告在没有授权实例覆盖时才回到最新 Profile。清除授权实例覆盖会把 `configuration_override` 写为空对象 `{}`，并把实例响应版本对齐到当前有效的下游配置版本或 Profile 版本；下一次响应不再返回旧覆盖值。底层配置在授权实例仍有覆盖时不替换该覆盖，待覆盖清除后才生效。

空支持信息返回 `support: null`；空或关闭的公告返回 `announcement: null`；授权 A 和核心页面隐藏对应区域。QQ、微信、标题和正文按纯文本处理，购买链接只允许 HTTP/HTTPS 且不带账号密码。

授权 A 的缓存不是平台事实源。缓存条目至少按 `software_id`、`profile_id`、`authorization_id`、设备范围和 `config_version` 隔离，并使用不超过 `expires_at`/`cache_until` 的有效期。服务端配置版本变化、授权 revision 变化、撤销、封禁、过期或 Profile 归档时，授权 A 必须刷新或失效对应条目；不能把旧缓存交给其他软件、其他客户或新的授权实例。

### Plan

必备信息：软件、名称、`duration_seconds`、额度成本、状态、生效时间和展示排序。套餐必须挂在某一个软件下；平台会接入任意数量的软件，每个软件独立维护自己的卡种和价格，不能共用一份全平台价目。新增软件只追加该软件的套餐，不得改写已有软件的卡种或成本。同名卡种（例如两个软件都叫“月卡”）仍是两条记录，价格、时长和设备数可以不同。

`duration_seconds` 必须是大于 0 的整数。管理端可以用分钟、小时或天等易懂单位录入，但保存、套餐快照和授权计算统一使用整数秒：`1 分钟 = 60`、`1 小时 = 3600`、`1 天 = 86400`。测试卡允许创建 1 分钟套餐，不需要为测试程序复制一套授权逻辑。

推荐时间规则：

- 内部保存 UTC 时间瞬间；`authorization.v1` 在线传输统一使用有符号 64 位 Unix epoch seconds（单位为秒、绝对 UTC 时间），不使用毫秒、浮点数或 ISO 字符串；报表和后台默认使用 `Asia/Shanghai`（北京时间）。应用不依赖 VPS 的本地时区设置。
- **响应里不得出现 JSON 浮点数（铁律，含启动票据所有时间字段）**：JCS 规范化遇到浮点直接失败，服务端签不出、客户端验不过，一个浮点字段会同时打死两端。服务端 `canonicalize_jcs` 遇到浮点抛错（签名前失败关闭，永不发出）；客户端解析器只接受无符号整数。所有时间戳一律整数 epoch 秒。
- `1 天`按 24 小时计算，`30 天`按 720 小时计算，`365 天`按 8760 小时计算。
- `expires_at` 使用排他结束时间；到达该时刻即失效。
- 两套钟不准改混：`expires_at` 是卡到期，激活时写进票，启动器交给主程序本地倒计时到点关；挤机 / 解绑 / 撤销 / 阻断只改平台绑定事实，旧设备必须再 `verify` 收到 `DEVICE_NOT_BOUND`（或撤销/阻断）才关。`cache_until` / `next_verify_at` 只决定启动器何时再问，不是核心到期。
- `cache_until` 与 `next_verify_at` 对 active、grace 和 not_modified 必须为 `min(expires_at, server_time + verify_interval_seconds)`，不能因为验证间隔而跨过 `expires_at`；`grace_until` 只是策略元数据，不能单独延长授权。
- `POST /api/v1/public/licenses/verify` 先做授权判定。硬失败不得被 IP `RATE_LIMITED` 覆盖；`RATE_LIMITED` 只用于绑定仍有效、只是问太勤。`activate` / `deactivate` 仍可在判定前限流。
- 公共限流按来访地址分池（更新再加软件/Profile），不是全站一个池。窗口是固定的：到期后该身份必须从 1 重新计数。不得因为软件还开着、继续按间隔来问，就把计数 TTL 续成缓存默认超时；也不得把加大次数当成修复。
- 有效期比较只能使用服务端可信的 UTC 当前时间；客户端提交的本机时间、时区或 `expires_at` 都不是事实。
- A/服务端按软件、Profile、授权实例和设备范围保存已接受的最大 `server_time`。引入 15 秒时钟漂移容限（`TIME_ROLLBACK_TOLERANCE_SECONDS = 15`），仅当时间倒退超过 15 秒才判定为篡改并返回不可重试的 `TIME_ROLLBACK_DETECTED`；微小 NTP 校准不误杀正常用户，响应时间强制使用历史高水位线。
- 回拨阻断必须**可恢复**：触发时实例与它的当前绑定一起进入 `blocked`，因此它不属于「冻卡」（冻卡的定义是实例阻断但座位仍占着）。管理端「解冻这张卡」必须能识别回拨阻断（`state_reason` 为回拨标记），把实例恢复为 `active` 并**只**把被回拨打断的绑定恢复为 `active`；管理员或风控单独阻断的绑定保持阻断。恢复动作写审计，带 `rollback_recovery=true` 与恢复座位数。不能只剩「撤销废卡」一条路。
- 默认禁止脱机：客户端均为在线联网程序，策略默认 `offline_grace_seconds = 0`。心跳持续失败或断网超过有效窗口时必须强制关停主功能，严禁脱机单机常驻。
- 生成授权卡密时写入套餐快照；之后修改套餐不影响旧卡。

当前 PR-03 的套餐必须绑定具体 `software_id`、`profile_id` 和 `policy_version`；套餐快照还必须保存生成时已验证的能力值。修改软件策略、能力定义或套餐不能回写历史快照或已生成卡密。

管理端新增套餐使用持久化 `PlanCreateOperation` 记录 `(actor, namespace, idempotency_key, request_hash)`；该记录、Plan 和第一个 PlanSnapshot 必须在同一事务中提交。缓存不可作为新增套餐幂等事实源；同一管理员重复提交同一键只返回原 Plan，换请求内容返回 `IDEMPOTENCY_CONFLICT`。

套餐生命周期先归档，再删除。管理员通过 `/api/v1/manage/catalog/plans/{plan_id}/status/` 将可用套餐归档或恢复：归档立即停止新发卡、下游目录和经营范围中的可用结果，但不改已发出卡密的效力。恢复必须重新检查软件、Profile 和当前策略处于可用状态。状态变更必须填写原因、使用持久化幂等事实并写 before/after 审计，状态变更本身不创建重复的 PlanSnapshot。

已归档套餐可通过 `/api/v1/manage/catalog/plans/{plan_id}/delete/` 删除：Plan 进入 `deleted` 墓碑，管理端目录、色块和套餐管理不再展示；不能恢复、不能再修订。删除是明确的失效动作，不是静默改写：该套餐全部历史快照下仍存在的卡密一律失效——`unused` 走回收作废并按原成本退回原下游额度（0 成本不伪造流水），`activated` 走授权撤销（卡密 `revoked`、实例撤销、有效绑定阻断），已回收/已撤销/已过期/已归档/墓碑卡跳过。Plan、PlanSnapshot、LicenseCard、LicenseInstance、DeviceBinding、额度流水和审计不物理删除。未归档套餐不能删除。PlanSnapshot、LicenseCardBatch、QuotaCardBatch 和 QuotaCard 的实例与 QuerySet 写入/删除都必须由模型层拦截，合法状态变化只能走业务服务。

套餐修订使用持久化 `PlanRevisionOperation` 记录请求哈希和脱敏响应；同一管理员同一键在缓存清空、进程重启或多 Worker 下仍只产生一个新快照，同键不同内容返回 `IDEMPOTENCY_CONFLICT`。经营范围写入使用持久化 `DownstreamSoftwareOperation` 记录目标下游、软件、请求哈希和响应，不能因缓存失效而把同一个幂等键改成另一组套餐范围。

短时测试套餐使用与普通套餐相同的 `duration_seconds` 和授权流程，并可带 `test_only=true` 标记。测试标记只影响管理端发卡目录、测试提示和审计，不降低服务端校验、设备绑定或撤销要求。

### SoftwareProfile / PolicyVersion / CapabilityDefinition

- Software/Profile 状态均为 `draft`、`testing`、`active`、`archived`。`testing` Software 只允许向明确开放经营范围的 active 下游展示和发行 `test_only=true` 的 active 套餐；普通套餐和任何未开放软件不得借测试状态发卡。`testing` Profile 可由公共授权 API 激活/验证/解绑，但请求身份仍必须完整匹配。`archived` Software 停止新发卡和 unused 首次激活；已激活授权继续 verify，直到自身到期、撤销或策略明确改变。`archived` Profile 不接受新激活。历史授权、卡密、设备和审计仍可查询。正式套餐额度成本必须 ≥ 1；仅 `test_only=true` 的套餐可以填 0。
- PolicyVersion 是不可变记录；实例 `save/delete` 与 QuerySet `update/bulk_update/delete` 都必须拒绝，只有创建新版本和明确的归档服务可以改变当前生效状态。管理端策略修订先读取持久化幂等操作再检查当前 active policy，Profile/软件归档不能改变已经完成请求的同键重放结果。
- 管理端修改现有授权参数只能创建新的 `PolicyVersion` 并归档旧版本；`software_id`、`profile_id`、`client_id`、`target`、`arch`、`channel` 等客户端身份字段不通过该入口修改。历史授权和当时的套餐快照保留其原策略引用；策略修订会给仍指向刚归档策略的套餐追加新快照，使后续新发卡使用当前生效策略。已发出卡密不改写。已激活卡下次激活换机读 Profile 当前 ACTIVE 的换机两项；下次 `verify` 读当前验证间隔。有效期、套餐和 `max_devices` 仍锁快照。
- CapabilityDefinition 至少保存键名、类型、默认值、范围、是否公开、所属 Profile 和版本。通用默认值可以由 Software 提供，但发布前必须解析到具体 Profile；唯一键为 `software_id + profile_id + capability_key`，不能跨软件或 Profile 覆盖。
- 未登记的能力键、错误类型和超出范围的值必须在保存/发布前拒绝；不能把任意 JSON 当作业务代码。

v1.0 允许同一软件同一设备激活多张卡，实际有效期取同软件、同设备所有有效授权实例中的最晚时间；不做复杂特性叠加。

设备与授权列表以授权实例为一行并按授权分页，多设备汇总在该行摘要与详情内。设备/风险筛选在服务端按授权归属计算，不能混入其他下游或软件；筛选命中的授权可在详情展示其有权限的完整绑定历史。卡密列表以单卡分页，软件、套餐、设备和期限筛选均在服务端分页前完成。

卡密明文不进入日志。需要再次显示时必须经过权限检查和加密解密；显示/复制/下载完整码不写“谁看过”审计。生成、回收、导出脱敏摘要仍审计。

授权卡密发行时必须绑定明确下游，但 `unused` 状态没有业务到期时间。第一次成功激活时才以服务端时间加套餐快照 `duration_seconds` 生成排他 `expires_at`，并创建唯一授权实例。**只有下游能为自己发卡**；管理员不能代发、不能绕过该下游账本出卡。管理员通过全平台卡密总表查询、搜索、显示完整码，并回收未激活卡（额度退回原下游）。下游发卡须重新校验经营范围、套餐和自身余额，并走扣额事务。

PR-05 可保留 `LicenseCardBatch`（或等价内部生成分组）作为发卡事务事实：保存软件、Profile、同一份 `plan_snapshot_id`、原始/当前下游、数量、单卡成本、总成本、来源、请求指纹和下游作用域内的幂等键；每张 `LicenseCard` 保存同一快照引用、成本、哈希、密文和生命周期字段。该对象创建后不可直接修改或删除，后续状态变化只能走明确业务服务。**页面不提供批次列表或批次号**；筛选、详情和多选都针对单码。

发卡时锁定当前下游和可用经营范围，锁定套餐并选定最新快照，计算总成本，再由外层事务调用 `credits.services.debit_quota`。额度不足、卡密碰撞超过重试上限或任意中途失败都回滚内部生成分组、卡密和额度扣除；零成本套餐不写入伪造的零额流水，但仍保留幂等和审计。总成本受 `LICENSE_CARD_MAX_TOTAL_COST` 限制。

成本预览由服务端签发带时效的签名令牌，绑定下游、软件、快照、数量、单卡成本和总成本；确认时必须重新验签并重新检查经营范围和余额。客户端改写隐藏字段、使用旧快照、修改数量或超过预览有效期都必须拒绝并要求重新预览。导出默认是脱敏单码摘要；完整卡密仍只能通过独立的 POST 查看/交付动作，不写“谁看过”审计。下载文件名不得含批次号。

PR-06 的回收规则：只有 `LicenseCard.status=unused` 的卡密可以回收；服务端从真实卡密读取原始下游、当前归属和 `quota_cost`，不接受表单或客户端改写。允许勾选部分未激活卡，也允许回收**当前筛选中的全部 unused 卡**；两种路径都必须先确认张数与返还额度，已激活卡不得进入回收集合。不再提供「回收本批」。回收在同一外层事务内锁定卡密、原始下游和非零返还所需的额度账户，把卡密改为终态 `reclaimed`、写入 `reclaimed_at`/状态原因，并按保存的成本产生一次正向 `LICENSE_CARD_RECLAIM` 流水。已激活、已过期、已撤销、已禁用和已回收卡密不能返还。零成本卡可以回收，但不写金额为 0 的流水。

回收使用确定性的卡密级幂等键；重复请求只返回原回收流水，不重复返还。回收与未来激活/状态变更统一遵守“先锁卡密，再锁原始下游，再锁非零返还所需额度账户”的锁顺序，任一步失败都不得留下“已返还但卡仍未回收”或“卡已回收但未返还”的半成品。原始下游档案被删除后，管理员仍可依据保留的 `downstream_public_id` 和额度账户完成财务补救；普通下游不能借此读取其他归属卡密。

管理员额度回收使用独立的 `recover_downstream_credits` 服务动作，固定写入 `ADMIN_ADJUSTMENT` 负向流水；管理员必须填写原因，服务端重新锁定账户并按账本余额拒绝超额回收。该动作不能通过通用客户端参数伪装成授权卡密扣款或人工充值。

### LicenseInstance

一张卡首次有效激活时创建唯一 `LicenseInstance`。授权实例保存：`authorization_id`、软件/Profile/套餐/策略快照、真实下游 UUID 快照、完整客户端身份、激活时间、排他有效期、当前状态、`authorization_revision`、`config_version`、撤销/阻断原因、最后验证时间、最后服务端时间和客户端版本。

数据库以 `LicenseCard 1—1 LicenseInstance` 约束一张卡最多一个授权实例。同时在线最大设备数由该实例生成时引用的不可变策略快照控制。是否允许换机和每个北京自然日换机次数读 Profile 当前 ACTIVE 策略，不改写实例上的策略引用。授权实例状态为 `active`、`grace`、`expired`、`revoked`、`blocked`。卡密到期后仍保持已激活/已过期事实，不能回到 `unused` 或再次生成第二个实例。

### 授权续期（ADR-0016）

管理员可以给**已激活且未过期**的授权补时间：实例 `state ∈ {active, grace}`、服务端当前时间早于 `expires_at`、卡密状态为 `activated`。未激活卡不消耗时间，因此不在续期范围内；已过期、已撤销、已阻断、已回收、已归档和墓碑卡一律拒绝。

续期是运营赠送，不是销售：只把 `LicenseInstance.expires_at` 与 `LicenseCard.expires_at` 往后推，并递增 `authorization_revision`，让客户端下次 `verify` 直接拿到新到期时间（不会被 `not_modified` 跳过）。套餐快照、`duration_seconds`、设备规则、下游归属、`quota_cost`、额度流水和收入口径都不变；不写账本、不写流水、不计收入。

已选一条或多条授权共用“加时间”；必须先明确选中范围，零勾选不代表全部。批量续期必须先预览再确认：预览按当前筛选返回冻结的授权 ID 列表和每条的新到期时间，确认只提交这批 ID，逐条独立事务，允许可追踪的部分失败并逐条汇报稳定错误码。单位只接受小时和天（3600 / 86400 秒），单次上限 366 天；续期后的到期时间不能超过这张卡激活起 10 年（防手滑连点），超出返回 `RENEWAL_LIMIT_EXCEEDED`。不提供缩短到期时间的入口。

两套钟不变：`cache_until` / `next_verify_at` 仍按 `min(expires_at, server_time + verify_interval_seconds)` 计算，续期只把 `expires_at` 推后。

### 启动票据（ADR-0018）

- 只签发给 `state ∈ {active, grace}` 且当前设备绑定有效的授权；过期/撤销/阻断/被挤下线逐条拒签，不返回 200 空票。
- 票据绑定单设备（`installation_id` + 设备公钥与当前绑定一致），受众按 `{software_id}-core` 派生，不按软件名分支。
- TTL 跟现行 ACTIVE 策略（默认 180 秒，策略 30–3600 秒可配）；开关 `launch_ticket_enabled=false` 的 Profile 一律拒签。
- 同幂等键重放返回同一张票，不重复签发；nonce 一次性，跨接口不可重放（签发与核销 proof 的 action 不同）。
- 核销必须同设备、未过期、未核销过；`ticket_id` 保留供扩展。票据行保留作审计，不物理删除。

### Device / DeviceKey / DeviceBinding

- `Device` 按软件、Profile 和 `installation_id`（稳定主板/硬件指纹，重装不得换值）的服务端 HMAC 哈希隔离，保存首次出现、最后验证、IP 和风险状态；指纹是设备身份输入，不能单独当作授权凭证，仍须 `device_proof`。
- `DeviceKey` 保存 Ed25519 公钥、稳定 key ID 和状态，不保存客户端私钥；同一公钥不能跨设备复用。
- `DeviceBinding` 保存授权实例、设备、设备密钥、绑定/解绑时间、状态、换机计数、最后服务端时间和原因；解绑、阻断、过期只追加历史状态，不删除绑定行。
- `Device.installation_id` 保存客户端上报的原始设备码明文，参与设备证明和服务端设备身份匹配；`installation_hash` 仍是设备身份与唯一性事实。`Device.device_code` 是由 `installation_id` 稳定派生的短展示码，只用于客服核对、授权/设备读侧展示和搜索，不参与授权判断。迁移前历史设备可以为空，之后同设备再次激活或验证时只补写空值，不覆盖已有明文。

设备证明签名绑定动作、request ID、完整软件/Profile 身份、安装 ID、公钥和一次性 nonce。nonce 只保存哈希并在成功证明后消费；同一 request/idempotency 重试**在记录保留期内**（默认 30 天，`AUTHORIZATION_REQUEST_RECORD_RETENTION_DAYS`）返回原结果，超期后原结果已不存在、同 key 重新提交按 `REPLAY_DETECTED` 拒绝，客户端须换新的 request_id/idempotency_key/nonce。不同请求重复 nonce 返回 `REPLAY_DETECTED`。服务端不保存私钥，也不接受客户端自行提交的有效期、下游或授权状态。

### QuotaCard

必备信息：面额、卡密哈希/密文、可选内部生成分组、发行者、状态、实际兑换下游、兑换操作者、兑换时间、来源 IP 摘要和作废原因。发行时不得预写目标下游，也不设置业务到期时间。`QuotaCard` 的 `redeemed_ip_digest` 只保存不可逆摘要，不保存兑换来源明文 IP；内部作废幂等键只服务一次性状态转换。

状态：`issued`、`redeemed`、`revoked`。发行后不再出现“指定下游”。历史目标字段在迁移中清除，已兑换记录保留 `redeemed_by` 主人事实。任一活跃下游登录后都可以提交完整额度兑换码；服务端从当前会话确定实际兑换下游并一次性原子入账，不接受请求参数指定或改写下游。同一码并发兑换最多成功一次，失败、限流和重复提交不改变任何账户余额。管理员可作废未兑换码；已兑换不能靠作废扣回。

额度卡密的查询哈希和密文加密密钥必须分离。新卡使用当前 `QUOTA_CARD_ENCRYPTION_KEY` 和 `QUOTA_CARD_ENCRYPTION_KEY_VERSION`（默认 `v2`）；历史 `v1` 卡只通过显式 `QUOTA_CARD_LEGACY_ENCRYPTION_KEY`/版本读取。轮换命令先默认只校验每一枚旧卡的密文和哈希，再在明确 `--apply` 后于事务内重加密并改版本；任一解密或哈希校验失败，整次迁移回滚。轮换后必须在隔离库重新 reveal、兑换和恢复验收，确认无旧版本行后才能移除历史密钥。

### QuotaLedger

每笔流水必须保存：下游、方向、整数金额、操作类型、来源对象、幂等键、操作人、原因、操作前可用余额、操作后可用余额和时间。

余额是流水汇总的缓存，不是唯一事实源。禁止通过页面直接把余额改成某个数字。

### QuotaPlatformSettings

额度卡购买链接是平台级设置，不属于某个下游或软件。只允许管理员保存空值或不含账号密码的 HTTP/HTTPS 地址；匿名登录/注册页和下游工作台只读返回当前值。保存使用幂等键并写审计；它不改变额度余额、卡密状态或授权期限。

购买链接保存的幂等事实单独保存在 `QuotaPurchaseUrlOperation`：每条记录绑定 `actor`、`idempotency_key`、请求哈希、该请求原始返回 URL 和创建时间，并以 `(actor, idempotency_key)` 唯一约束隔离管理员和动作。服务端事务先锁定平台设置行，再查找或创建操作记录；同一管理员同一键同一内容只返回记录中的原始 URL，不再次修改当前链接或写成功审计；同键不同内容返回 `IDEMPOTENCY_CONFLICT`；旧键在新键之后重试也不能覆盖当前链接。设置表上的 `last_idempotency_key`/`last_request_hash` 只作为旧版本兼容元数据，不替代操作记录。

## 状态转换

### 授权卡密

```text
generated → unused → activated → expired
              │          │
              ├→ reclaimed  └→ revoked / disabled
              └→ revoked / disabled
```

`reclaimed` 是终态，不能回到 `unused`。已激活、已过期、已撤销或已禁用卡密不可回收返还额度。

### 设备绑定

```text
pending → active → unbound
             ├→ blocked
             └→ expired
```

解绑不删除历史。换机限制是为了防止一张卡被多个人/多台电脑轮流共享滥用。对于已激活的授权实例，坑位已满时新设备介入必须校验换机开关并消耗当日换机次数（每个北京自然日 N 次）；坑位未满时，从未接入过的新设备首次填坑不计次，但历史旧设备切回（与最后一次活跃设备不同）仍计次，防止交替解绑轮换套利；当日换机次数耗尽立即拒绝（`DEVICE_SWITCH_LIMIT_REACHED`）。同一台物理电脑（硬件码一致）同钥解绑后重新登录激活，属于原机恢复，不消耗换机次数；同机重装换新公钥走自愈轮换，计 1 次当日换机额度（额度为 0 的策略不拦截但仍计数），防持卡冒用硬件码无限乒乓劫持。管理员支持批量撤销授权、批量封禁设备与批量解封设备（解封只移出黑名单，不复活旧座位），写不可变幂等记录与审计。

设备绑定及活跃换钥使用授权实例锁内分配的持久递增序号判断先后；迁移前记录序号为0，不以随机UUID推断同秒先后。旧同秒多钥且无ACTIVE的历史按轮换保守计次，成功后建立可靠顺序；有ACTIVE时以当前有效绑定判定同钥恢复。兼容处理保留原时间、密钥、状态和授权期限，审计标明无法证明的历史顺序，不猜测旧密钥。

### 下游

```text
active → suspended → closed → deleted (tombstone retained)
```

关闭后不能登录、生成卡密、使用额度或发起新的授权业务，但历史数据保留。

### AuditEvent / 审计查询

- `AuditEvent` 是不可变事实：普通 ORM 更新、批量更新、实例删除和 QuerySet 删除都必须被拒绝；查询、分页和导出只能读，不改变历史记录。
- 管理员按 `platform_admin` 角色查询全平台事件；普通 `is_staff` 不自动获得审计权限。活跃下游的范围从当前会话关联的 `DownstreamProfile` 推导，不能使用查询参数中的下游、软件或对象 ID 扩权；暂停/关闭下游不能进入下游工作台，管理员仍可查询其历史。
- 下游范围必须在 SQL 中收窄（actor、metadata 归属键、以及该下游卡密/额度/授权/设备对象 ID 的 IN 子查询），返回 QuerySet；禁止先 `iterator` 全表再在内存里过滤或分页。无法可靠归属的匿名事件只对管理员可见。
- 日期筛选按北京时间日期解释，再转换为 UTC 半开区间 `[from, to)`；排序固定为最新时间和公开 ID 倒序。动作、结果、对象类型和对象公开 ID 使用固定字段精确匹配，不接受动态 ORM 字段或 `order_by`。
- 列表查询使用服务端分页：`page` 与 `page_size`（默认 50、最大 100），`count`/`has_next` 必须来自过滤后的 QuerySet；冻结 8123 审计页每次请求 10 行并提供上一页/下一页，禁止先拉 50 条再在浏览器里切页。
- 页面和 CSV 只输出固定投影：请求 ID 保留稳定摘要；管理端和下游端的 IP、设备/授权对象 ID 及其他非凭证业务字段按读侧权限明文返回。卡密、额度兑换码、密码、Token、私钥、原始请求内容和原始 metadata 不得进入查询响应或导出，卡密/额度码只允许按脱敏尾号或受保护的按需动作交付。metadata 仍只允许金额、状态、版本、公开 ID/哈希摘要等白名单键。CSV 单元格还必须拒绝公式前缀。
- 管理员与下游 CSV 导出都复用页面筛选和权限，最多导出 1000 条（SQL LIMIT）；卡密/额度码仍不导出完整值，设备、IP 和其他非凭证业务字段按读侧权限明文导出。导出成功或筛选失败本身写入审计。对象摘要用于追溯额度账户/流水、授权卡密/实例和设备绑定，不把当前对象状态当成历史状态替代。
- 密码操作的 `auth.password_change`/`auth.password_reset` 事件与 `PasswordOperation` 记录都属于管理员可追溯事实；下游只能看到自己的登录/操作范围，不能查询或修改密码操作记录。

## 关键业务不变量

1. 卡密只能归属于一个软件。
2. 下游只能操作自己拥有或被授权的数据。
3. 生成卡密、扣除额度、写入批次必须在同一事务内完成。
4. 回收卡密、改变卡密状态、返还原始额度必须在同一事务内完成。
5. 同一额度卡、同一回收请求、同一生成请求重复提交不得产生第二次效果。
6. 额度不能因为并发操作变成负数，管理员回收不能超过可用额度。
7. 审计记录和额度流水不物理删除；可归档的业务对象在删除后必须保留最小脱敏墓碑或可追责引用，不能让历史流水变成无法解释的孤儿记录。
8. 服务端不接受客户端提交的 `expires_at`、`downstream_id` 或授权状态作为事实。
9. `software_id`、`profile_id`、`client_id`、`target`、`arch` 和 `channel` 的组合必须与服务端登记完全匹配；不匹配不得降级到其他软件或 Profile。
10. 软件适配器不能直接改变额度、卡密、授权实例、设备绑定或审计事实；这些只能由通用应用服务事务完成。
11. 新增软件、Profile 或能力定义只能影响自己的命名空间；归档、策略更新或适配器故障不能改变其他软件的数据和状态。
12. 能力和策略更新必须生成版本或快照；`PolicyVersion` 和 `PlanSnapshot` 创建后不可直接修改或删除；已经生成的卡密和授权实例不能被静默改写。
13. 到期判断使用服务端 UTC 当前时间，`server_now >= expires_at` 即失效；修改客户端本机时间不能延长授权。
14. 测试卡与正式卡共享同一授权事实、状态机和安全边界；`test_only` 不能成为绕过设备、撤销或审计的后门。
15. 邀请码不预绑下游、未使用前无期限且一次只能消费一次；注册失败不创建账号、不消费邀请码；并发注册最多一个成功。
16. 下游对象权限从会话身份和 Profile 状态推导；修改 URL 或表单中的其他下游 ID 不能扩大可见范围。
17. 活跃下游必须先归档才能删除；删除保留脱敏墓碑或可追责引用。
18. 中央平台公共授权 API 只能由对应软件的授权 A 调用；核心 EXE 不直连中央平台，中央平台也不主动连接核心 EXE。
19. 授权 A 只能把自己软件、Profile、授权实例和设备范围内的类型化结果交给核心；本地合同失败、身份不匹配或签名无效时核心必须锁定受保护功能。
20. 联系方式、购买链接、公告和更新元数据必须由服务端按真实授权归属解析；客户端提交的 `downstream_id` 不能改变结果。
21. 客户覆盖优先于下游-软件默认配置；没有配置返回空值，不使用其他下游或其他软件的默认值填充。
22. A 层缓存至少按软件、Profile、授权实例、设备范围和配置版本隔离；缓存不能延长授权、覆盖撤销/封禁，也不能跨客户复用。
23. 更新、公告和配置只以版本化、类型化数据传递；平台和授权 A 不能下发任意脚本、命令或 DLL 路径。
24. 激活、验证和解绑事务按“卡密 → 授权实例 → 设备 → 设备密钥 → 当前绑定”顺序获取锁；设备上限检查必须在授权实例锁内完成，失败不得留下孤立设备、密钥或绑定。
25. 授权响应只接受精确小写 `ed25519` + `JCS-RFC8785`；签名覆盖删除 `integrity.signature` 后的完整响应，未知 key/算法/规范化或签名错误必须 fail closed。对象键按 RFC 8785 的 **UTF-16 码元序**排序，不是 Python 码点序；键含辅助平面字符时两者结果相反。
26. `server_time` 采用 UTC epoch seconds，`server_time >= expires_at` 即过期；服务端或 A 发现已接受时间回退时返回 `TIME_ROLLBACK_DETECTED` 并阻断当前授权范围。该阻断可由管理员解冻恢复（见上文时间与反绕过一节），不属于不可逆终态。
27. 设备风险状态 `blocked` 返回不可重试的 `RISK_BLOCKED` 普通错误并禁止缓存；授权实例状态 `blocked` 才能通过签名 `decision=blocked` 信封表达。
28. 额度兑换码不预绑下游、未兑换前无期限；实际兑换下游只能来自当前活跃登录会话，同一码最多入账一次。
29. 授权卡密必须绑定下游、未激活前无期限；只有下游发卡。管理员不代发，全平台总表只监管与回收未激活卡。
30. 设备重置只撤销当前 `DeviceBinding`，不得重置 `LicenseInstance.expires_at`、套餐快照或授权收入事实；必须保留解绑前设备、操作者、时间和原因的审计引用。已激活卡的设备/IP/到期排障信息只出现在设备读侧和审计，不与未激活卡库存表重复。
31. 管理端下游生命周期为 `active → suspended ↔ active → archived → deleted_tombstone`；只有归档下游可以删除。暂停会阻止登录和新业务，归档会阻止登录和业务，删除只保留最小脱敏追责引用；每次状态变化必须带操作者、北京时间、原因和审计引用。密码正确的暂停下游登录失败文案为「账号已暂停。」；密码错误或走错门仍用「用户名或密码不正确。」。
32. 管理端“设备与授权”是已激活客户的读侧与处置入口。设备重置、设备封禁/解封、授权撤销和归档删除各自保留独立状态语义；设备重置不得被实现为撤销授权或延长时间，解除设备封禁也不得复活历史绑定。
33. 审计事件至少保留北京时间、操作者类型/身份、来源、动作、结果/稳定错误码、下游、软件/Profile、脱敏卡密、授权/设备引用、IP、request_id、原因或前后变化摘要；不得保存完整卡密、密码、令牌或私钥。
34. 管理端授权诊断按授权实例返回全部设备，而不是只返回“最新一台”；设备历史按物理设备分组，`devices[]` 中每项保留当前状态和 `binding_history[]`，设备 ID 和 IP 按管理端读侧权限明文返回；卡密/额度码仍按凭证规则保护。
35. 管理员设备重置的资源范围必须同时包含 `authorization_id` 与 `device_id`；共享设备可绑定多个授权时，只能解绑目标授权的当前绑定，不能按设备 ID 全量解绑。
36. 管理员风险处置动作必须使用 CSRF、原因和持久化幂等键；`AuthorizationAdminOperation` 是不可变操作事实，同一管理员和幂等键的请求哈希、动作或目标不一致必须返回 `IDEMPOTENCY_CONFLICT`，不能重复改变 revision 或状态。
37. 管理员撤销、封禁、解封和重置的审计必须包含适用的 before/after 状态、revision、卡密状态、绑定数量和目标引用；失败审计不得伪造成功结果，解除封禁不得复活历史绑定，页面刷新后状态以服务端读侧为准。
38. 密码操作不保存任何密码原文；同一操作者和幂等键只能对应同一动作、目标和请求 HMAC，换请求体必须返回 `IDEMPOTENCY_CONFLICT`，重放只返回原脱敏结果。
39. 自助改密只能修改当前会话身份；管理员重置不能使用客户端提交的租户/角色字段扩展目标，归档下游不能被重置。
40. 密码成功变更后，管理员当前会话保留；下游当前会话只保留新的 `session_version`，所有其他旧下游会话必须失效；管理员重置不得影响管理员自己的会话。
41. 密码变更和重置按账号/目标/IP 组合限速，429 必须返回稳定错误码和 `Retry-After`；限速、CSRF、越权和失败校验都不得泄露密码或原因原文。

## 授权优先级

按以下顺序拒绝授权：

```text
请求格式/签名错误
→ 软件不存在或不匹配
→ Profile/客户端身份或授权 A 合同不匹配
→ 下游/软件关系无效
→ 卡密不存在、未激活、已过期、已禁用或已撤销
→ 授权实例或设备被撤销/封禁
→ 设备数或换机规则不允许
→ 版本或风控策略不允许
→ 授权成功
```

软件暂停、下游暂停和缓存宽限期的具体影响必须由软件策略决定并记录；安全撤销优先于一切宽限。PR-08 的默认下游级联策略是：下游暂停/关闭会阻止新的卡密激活、换机或新增设备绑定，但不自动撤销已经存在的授权实例；已有绑定继续验证，直到授权自身到期、撤销、设备阻断或策略明确改变。这样既停止新增业务，又避免把渠道状态变更误当成客户授权事实。经营范围关闭 ≠ 账号暂停/关闭：账号暂停/关闭仍拦新激活和换机；关掉某下游某软件经营范围只拦该下游该软件 unused 首次激活，不拦已开通 verify，也不拦已开通换机。

PR-08 的基础异常规则分为两层：时间回退、已阻断设备、设备密钥跨设备复用和 nonce 重放由授权服务即时拒绝或 fail closed；设备证明失败、身份不匹配等高信号失败进入管理员待复核队列，但单次普通失败不自动封禁。待复核队列只展示脱敏的动作、稳定原因码和 request_id 摘要，不替代服务端授权判断。管理员风险动作的越权尝试也写入失败审计；设备绑定集合在阻断期间变化时事务回滚并重试，避免漏阻断。

风控记录只提供核对线索，不以失败次数、IP变化、断网、重装或客户端自报调试器作为自动冻卡依据。未知归属不得按请求自报ID关联处罚；页面明确“全平台最近50条”，保留来源动作、稳定原因码、服务端记录时间、信号ID和请求摘要。先修复接入/重试配置，核实服务端授权和绑定后才由管理员确认单卡冻结并写原因；解冻不延长到期、不释放座位、不解封其他风险设备。服务端可信时间回拨属于平台时间问题，不能表述为客户作弊。

软件重新上架只将archived恢复为active，不恢复下架时关闭的DownstreamSoftware；必须由管理员明确重新开放经营范围。状态操作保留原因、before/after及持久幂等事实。

启动票据签发重放/核销不能覆盖当前授权终态、到期、风险、解绑或禁票。票据TTL受授权到期上限约束，核销只接受当前有效绑定。

## 并发与幂等

- 所有写操作接收 `Idempotency-Key`。
- 邀请码消费和下游注册使用行级锁或等价数据库并发控制；重复提交返回同一失败/成功业务结果。
- 授权请求的历史放行结果必须同时匹配当前授权 revision、状态、设备风险和 `expires_at`；撤销、阻断、解绑、过期或配置变化后，同一键不能重放旧的 `active` 响应，统一返回不可重试的 `IDEMPOTENCY_CONFLICT`。
- 额度账户在扣除、返还和管理员回收时锁定或使用等价的数据库并发控制。
- 同一张卡的激活请求可重复返回同一结果，但不能为不同设备绕过设备限制。
- 批量生成支持明确的全成或可追踪部分失败，不允许静默丢卡或多扣额度。
- 未激活卡回收支持明确卡 ID；筛选预览返回冻结的 `card_ids`，确认必须提交这些 ID，不得按 `selection: filtered` 再活查。筛选状态强制为 `unused`，下游归属来自当前会话。批量回收按稳定公共 ID 顺序获取卡密/额度资源锁，API 幂等记录的唯一键竞争必须在保存点内处理。下游与管理端回收都要可追溯原因。
- 密码自助修改和管理员重置先按操作者串行化幂等操作，再锁定目标 User/Profile；同一幂等键并发最多一次改密，失败或重放不能重复递增 `session_version`。
- 事务失败时不写成功审计，不产生孤立额度流水。
- Profile 发布、能力定义发布和适配器登记也必须幂等；失败时不能留下“可见但不可用”的半发布配置。

## 版本发布与受控存储

- `Release` 必须同时保存软件、Profile、版本、平台、架构、通道、`client-release.v1` Manifest、服务端重新计算的包大小/SHA-256、签名算法/Key ID/签名状态、说明和发布状态。上传草稿、确认发布和撤回均使用持久化幂等操作记录并写审计。
- `ReleaseSignatureStatus=declared` 只表示 Manifest 携带了 ed25519 声明；只有服务端配置的公钥验证通过才是 `verified`。生产可要求 `verified`，不得把 `declared` 当成已验证签名。
- 公共 registry 和下载只允许 `Software.status ∈ {testing, active}` 且 `SoftwareProfile.status ∈ {testing, active}`；草稿、归档或其他不可用对象返回不可见/不可下载。撤回保留历史且不立刻删除安装包 ZIP，查询时回退到同一软件/Profile/平台/架构/通道下剩余已发布版本中版本号最高者；没有剩余已发布版本则公共 registry 无当前包。管理员可对已撤回且包仍在磁盘的版本单独删除安装包，状态保持 `withdrawn`，版本号仍占用；已发布包不可删。
- 发布包路径必须解析到受控 release root 内的普通文件；绝对/相对越界路径、任意符号链接、缺失或非文件一律不可下载。下载文件名是安全投影，不从路径或原始上传名注入响应头。
- 受控存储清理只处理超过保留期的撤回包、`tmp/`、`exports/` 和 `logs/` 文件；删除前必须重新检查路径、符号链接、文件类型、大小和已记录 SHA-256，发生篡改、变化、竞态消失或越界时跳过。清理不删除审计、额度流水、卡密、授权实例、设备、账号或其他业务事实，也不删除下载表 `BACKUP_DOWNLOAD_DIR` 里的 `.enc`。
- `ReleaseStatus` 含 `draft`、`published`、`withdrawn`、`discarded`、`archived`。归档只作用于 `published` 或 `withdrawn` 版本，**不必先撤回**；归档后从默认版本列表消失，`archived_at`、`archived_from_status` 和归档原因保留，版本号仍占用。归档一个已发布版本等于同时下架：公共 registry 回退到同一软件/Profile/平台/架构/通道下剩余已发布里版本号最高者。重发同一个版本号会复活被归档的行并清掉归档标记。
- 已发布版本可以就地修改版本号（例如 `2.0.8` → `2.0.9`），用于「网盘地址不变、只替换文件」的场景。新号必须三段数字、不得与同范围另一条未丢弃版本冲突、必须高于该范围其他已发布版本（即改号等于把这个版本提到最新）。改号同步更新记录与 Manifest 的 `version`，审计保留前后值。已撤回版本不改号（改完客户端也看不到），草稿请丢弃重发。

## 统计口径

- 今日、本月按 `Asia/Shanghai` 的自然日和自然月计算。
- 数据库存储和接口时间仍使用 UTC；只有展示层和统计边界转换为北京时间，不能把 VPS 时区作为业务配置来源。
- 今日、本月、累计收入默认指已激活卡密的套餐额度成本之和，未激活不计；单位是额度，不是人民币。一张卡按发卡时锁住的套餐额度成本计入，例如 10 张月卡（每张 10）加 5 张天卡（每张 1）激活后是 105。0 成本测试卡激活后收入仍是 0，不能拿「活授权」个数冒充收入。管理端累计等于各下游累计之和；下游只看自己。生成量、激活量和回收量可单独列出，但不能冒充收入。
- 活跃设备默认指最近一次成功验证在配置窗口内的设备，窗口值必须显示在统计说明中。
- 即将到期默认指未来 7 天内到期的有效授权，可由管理员配置。

## 凭证显示与历史处置

所有凭证的归档都是低风险分类动作：已过期、已撤销、已回收、已兑换或已消费的终态凭证可直接归档，归档后从默认当前列表移入归档分类；下游单卡列表永远排除归档卡，也不能用 `status=archived` 或 `scope=archived` 把它们读回来；下游精确搜索完整码同样排除归档卡，归档码与不存在一样返回 `LICENSE_CARD_NOT_FOUND`。有效未使用授权卡仍需先回收，未兑换额度码和有效未使用邀请码仍需先作废/撤销。删除是后续不可逆的墓碑动作，只接受已归档记录，审计、流水、授权、设备历史和密文继续保留（密文只供恢复核对，不得清空）。删除后 search/reveal 与发行同键重放均按不存在处理，不得从保留密文再交付完整码；批次内仍有未墓碑卡时，重放只交付那些码，不新发一批、不再扣额度。
- 审计记录和额度流水不可删除。删除有历史引用的业务对象时，保留可追责的脱敏历史引用。
- 卡密、邀请码和额度兑换码在授权范围内可以重复查看、复制或下载；完整码显示/复制/下载不写“谁看过”审计。日志不保存完整明文。生成、兑换、作废、回收、撤销仍审计。
- 列表默认脱敏，但单码详情必须能经授权显示完整码。输入完整码进行精确搜索时，真实 Web 端只把值提交给服务端做 HMAC/哈希匹配，不把明文放进 URL、日志、隐藏 DOM、通用导出或分析事件。
- 密码不提供原文查看，只能重置。这个规则与“运营凭证可重复交付”分开处理。

## 备份、恢复与迁移不变量

定时 full 槽位补充：只有定时 `PENDING` 携带的 `scheduled_for` 才能形成供巡检去重的计划槽位 stamp；巡检按精确计划槽位去重，修改北京时间全量时刻会产生新的槽位；没有计划槽位的手动或变动 full 只能记录普通完成时间，不得被当作当天定时 full，也不得覆盖已完成的计划槽位。

42. 当前Docker备份为独立完整PostgreSQL逻辑导出并加密成.enc；full/diff是调度类型，不是PITR差异链。数据库、原密钥和已发布安装包对象必须分别保管，.enc不包含对象文件或密钥。
43. 默认本机加密.enc，可由负责人配置GitHub额外副本；不保存明文密钥或明文数据库，不把同盘多个文件当成异地保障。独立远端读回和恢复证据必须实测，不因开关为true而视为具备。
44. 运行成功、dump完整性与严格proof分别记录；严格proof marker仍核对版本、迁移、dump/对象/恢复清单及证据哈希。当前dump_only缺少双仓/WAL proof时应如实标明证明未齐，不能伪造PITR成功，也不能否认已完成的本机导出。旧启动环境声明门仍保留兼容校验，不代表实际运行了双仓设施；失败状态及外部通知的实际可见性须单独验证。
45. 恢复验收必须在新建隔离数据库/对象前缀中运行，源库与恢复库分别生成脱敏 inventory；PostgreSQL 源库 inventory 使用一致性读取快照；行数、状态、密文指纹、密钥版本、逐账户额度流水链、余额、授权实例、设备/绑定历史、软件/Profile/能力/套餐/下游经营范围、版本对象元数据、审计时间线和持久化操作记录不一致时不得切流。
46. 恢复验收必须使用对应密钥版本在内存中解密邀请码、额度兑换码和授权卡密，并重新核对 HMAC；明文不得进入清单、日志、URL、测试报告或通用导出。
47. 额度恢复校验按账户逐笔检查 `balance_before`、方向/金额、`balance_after`、下一笔衔接和最终 `QuotaAccount.available_balance`；只比较全局总和不算通过。
48. VPS 迁移先保留旧服务、数据库卷、对象副本和密钥恢复材料，完成新环境隔离恢复与业务清单核对后才允许切换；`--compare` 默认拒绝同一数据库身份自比，不能把当前库自己比自己写成隔离恢复。最终删除旧资源必须另行确认，不属于自动迁移步骤。
49. 管理端备份策略是单例且可审计；`enabled` 是备份总开关，`schedule_enabled` 是定时排队开关。打开 `enabled` 后，生成新卡、卡密激活、额度账本变化会排队备份（短时间多次变动只排一份），变动触发器和每 15 分钟的主机策略巡检共用同一个 `PENDING` 队列。关闭 `enabled` 后不再为新变动或新定时任务排队，但不删除既有备份，也不阻止已排队任务；关闭 `schedule_enabled` 只阻止新的定时排队，不影响变动触发的队列。巡检看到已有 `PENDING` 时不得重复创建，并必须补写 `need-run`；有未超时 `RUNNING` 时等待，超过 90 分钟的 `RUNNING` 标为失败后再排队。全量时间使用北京时间；定时全量 `PENDING` 必须保存本次北京时间计划槽位对应的 `scheduled_for`，主机成功 stamp 绑定该槽位；任务跨北京时间午夜完成也不得占用下一自然日的 full 槽位。全量与增量同时到期时全量优先。`need-run` 只是 systemd.path 的唤醒信号，数据库记录是事实源，dispatcher 按 `backup_type` 选择 full/diff runner。旧 full/diff 日历 timer 禁止启用，不能绕过页面策略。每一次执行先在本机写加密 `.enc`，GitHub 是额外拷贝；加密包每个去向最多留 3 份，满了覆盖最旧的。备份不再拷到 Cloudflare R2、S3 或 WebDAV 网盘。主机 root 写入 `backup-stamps/`，应用容器只读 stamp。主机 runner 认领排队后 dump；GitHub 只推 `recovery-manifest.json` 与 `dumps/*.enc`，在本机加密包就绪后即可推送，不等待对象清单证明；成功 marker 仍要 proof。开启 GitHub 时必须有仓库和令牌。当前单体 Docker 部署下跳过外部 pgBackRest 双仓，full 与 diff runner 均执行独立完整的数据库加密导出，每次生成的 .enc 均具备单文件独立恢复能力，不依赖历史差异链。
50. 管理端下载只允许配置下载目录下的加密 `.enc` 普通文件；不提供明文数据库导出，不允许路径穿越或符号链接。GitHub 凭据加密保存，API 只返回是否已配置。备份文件与恢复口令必须分开保存。下载表可受控删除单份 `.enc`，必须确认并至少留 `max(1, github_retention_count)` 份，禁止删光最后一份可下载灾备；不得因此去删 pgBackRest 仓库。页头存储清理不含下载表 `.enc`。
51. 清理只作用于超过保留策略的备份/临时残留候选；执行前展示候选数量和大小，审计、额度流水、业务对象和墓碑不得删除。立即备份只创建排队记录，不得在 Django 请求内执行主机备份程序；主机 `backup_policy --decide` 必须认领排队并回写成功或失败。
52. 管理端导入恢复只能在空站点继续：软件、套餐、授权卡密、授权实例、额度卡、下游、邀请码、下游墓碑、额度账户和额度流水计数必须全为 0；允许已有引导管理员、登录审计（含当次导入核对审计）、备份策略、排队记录和导入暂存。不得把管理员 User、AuditEvent、BackupRestoreStaging、BackupPolicy、BackupRunRequest 算进非空。导入前必须解密并核对比京时间，确认值必须与显示时间一致，不要抄文件名。非空站点口令对了也拒绝导入（人话：文件和口令对，但当前有业务数据，不能导入。），不得覆盖当前业务数据。口令不得入库或写入审计。非 PostgreSQL 环境只完成核对，不执行 `pg_restore`。空站点且 PostgreSQL 时，网页确认导入仍对当前库执行 `pg_restore --clean`。
53. 每条发布必须有版本号；客户端带当前版本询问，平台返回最新版和 `has_update`。默认更新打开网盘地址。本站 ZIP 谁都能下，只按 IP 限流；生产不得把 `PUBLIC_RELEASE_DOWNLOAD_IP_RATE_LIMIT` 设为 0 或负数。不得把卡密放进下载网址，不得给 `/api/` 加 CORS `*`。
54. 不得同时暴露旧 HTML 写页和冻结控制室两套运营真源。旧批次页/导出、揭码、回收、邀请/额度/目录/版本/备份等 HTML 写入口默认即返回 410（正文「请从当前控制室进入。」），当前用户只使用 `/api/v1/` 与冻结页。
55. 平台密钥全生命周期只承认一套（ADR-0015）：任何 VPS、候选、测试授权平台部署都必须注入 `部署与恢复/灾备钥匙包` 中的现行卡密/额度加密密钥、Django SECRET、发布验签私钥和 dump 口令，禁止再生成。GitHub 登录令牌、Let's Encrypt 证书可更换，不算这套锁。本地可丢弃夹具和旧测试账本不是客户恢复点；现行正式业务必须保留。
