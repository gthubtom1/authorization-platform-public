# 多软件适配与隔离方案

**2026-11-16 现行接入入口：** `接入说明/00-先读我.md`。平台后台创建并下载 `software-bind.v2`（内含公钥、09 指令与 protocol 原文），在软件项目使用模板副本并接核心。以下技术边界仍有效；旧手填空白清单、先等待平台 AI 登记/回填身份的顺序已被替换。实际模板和软件兼容性需在副本内验证，不能由本平台导出测试代替。

## 结论

“通用”不等于把所有软件的特殊字段塞进一张万能表，也不等于每增加一个软件就修改授权核心。平台采用三层边界，并把平台侧适配器和产品侧授权 A 分开：

```text
中央授权平台（通用授权核心）
  → 版本化 SoftwareProfile / Policy / Capability
  → 可选的、隔离的平台侧 SoftwareAdapter
                    │ HTTPS
                    ▼
每个软件独立的授权 A（授权页 / Launcher / 缓存 / LocalBroker）
                    │ /local/v1
                    ▼
该软件的核心 EXE
```

中央平台不直接连接核心 EXE；每个软件的授权 A 独立维护，A 只把当前软件的、经过合同校验的类型化结果交给自己的核心。文档负责定下规则，但文档本身不能保证隔离。真正的保证必须同时落在：数据库约束、服务层选择器、两段 API 合同、自动化测试、审计和发布门禁。平台公共实现已部署，本文规定当前扩展与隔离边界；具体 EXE 的源码、模板兼容和验收属于该软件项目。

## 两种适配器不是一回事

| 名称 | 所在位置 | 作用 | 不允许 |
|---|---|---|---|
| 平台侧 `SoftwareAdapter` | 中央平台代码/注册表 | 处理公共合同无法表达的少量服务端产品语义，返回标准授权决定 | 不能按软件名污染核心；不能执行数据库脚本；不能直接改额度、卡密或审计 |
| 软件侧“授权 A” | 每个软件自己的 Launcher/分发目录 | 展示授权页，调用平台，缓存结果，通过 `/local/v1` 把结果交给自己的核心 | 不能携带管理员密钥；不能替平台决定有效期；不能把 A 的数据交给 B |

“授权 A”是产品接入层，不是平台数据库里的一个可执行插件。平台只登记它对应的 Profile、合同版本、公开能力和发布状态。

## 能支持什么，不能承诺什么

### Tier A：默认直接接入

只要客户端是联网程序，并且授权可以表达为以下生命周期，就不需要改授权核心：

```text
activate → verify / session-refresh → deactivate
                         └→ device switch（若软件策略允许，按独立策略动作处理）

旧客户端动作名只作为接入发现结果：`validate` 映射到平台 `verify`，`heartbeat` 映射到授权 A 的本地 `session/refresh`；不因旧名称在通用适配器中新增未冻结的平台路由。
```

可通过配置改变：最大设备数、换机次数、验证间隔、有限断网宽限、最低版本、套餐有效期、软件级客户端配置和功能额度。默认验证间隔 60 秒；已售卡下次 `verify` 读当前 ACTIVE 策略间隔。禁止按软件名在核心堆 `if software_id`。挤机可见性靠启动器 `verify`，不靠核心到期倒计时，也不靠限流盖住 `DEVICE_NOT_BOUND`。

### Tier B：仍然不改核心，只增加声明式能力

软件可以声明自己的命名空间能力，例如 `feature.export`、`limit.projects`、`edition.pro`。这些能力必须有类型、默认值、取值范围和是否公开给客户端的定义。套餐只分配已登记的能力，不允许把任意 JSON 当作后端代码执行。

### Tier C：需要平台和客户端一起改

只有当新软件需要全新的动作或协议语义，例如浮动席位、用量计费、长期离线租约、SSO 或新的设备证明方式，才进入扩展评审。扩展必须使用新的模块或协议版本，旧软件继续使用原版本。

### v1 明确不承诺

“任何软件都能接入”不能被解释成自动支持所有授权模型。v1 的默认边界是在线、服务端判定、卡密激活、设备绑定和短期验证。浮动授权、长期离线、支付、SSO 和复杂企业审批属于后续独立能力，不通过偷偷增加字段解决。

## 对象和所有权

### Software

人能理解的产品名称和稳定 `software_id`。它是隔离根，不在代码中写死某个软件名。

### SoftwareProfile

同一软件的一个客户端接入身份，至少包含：

- `profile_id`：如 `stable`、`beta`，同一软件内唯一。
- `client_id`：客户端应用稳定身份，不随版本号变化。
- `contract_version`：使用的公共协议版本。
- `target`、`arch`、`channel`：目标平台和发布通道。
- `adapter_key`、`adapter_version`：默认使用 `generic-online-v1`；特殊适配器必须显式登记。
- `status`：`draft`、`testing`、`active`、`archived`。

软件、Profile、客户端版本和发布包是四个不同对象，不能用一个“当前版本”字段代替。

### 软件授权 A（Authorization A）

每个 Software 至少有一个独立的授权 A 目录/包，负责四件事：

1. 在授权页接收最终客户卡密、展示购买链接和下游联系方式；
2. 使用该软件固定的 Profile 身份调用中央平台公共 API；
3. 按授权实例、设备和配置版本缓存中央返回的短期结果；
4. 通过版本化的 `/local/v1` 本地合同向自己的核心 EXE 提供授权状态、能力、联系方式、公告和更新元数据。

授权 A 不把平台主密钥或管理员凭据放入核心 EXE。默认本地传输只绑定 `127.0.0.1`，使用短期本地会话令牌，失败时核心必须锁定受保护功能。授权 A 的代码、版本、缓存和测试证据属于产品自己的目录，不能写入中央平台公共源码或与其他软件共用可变状态。

公告沿 `SoftwareProfile` 默认 → 当前真实 `DownstreamSoftware` 配置 → `LicenseInstance.configuration_override`。渠道通知 `support` 只跟发卡下游在下游页填的购买 URL 和联系方式；Profile 同名字段不是候选，没填则空。Profile与下游配置保存仅更新提交字段，省略保留本层原值，显式空串清空；实例覆盖仍为整份替换。清除下游层关闭 `configuration_enabled`，清除授权实例覆盖置为空 `{}`；响应只使用 `support`、`announcement`、固定五键 `modules` 和不透明 `config_version`。授权 A 的缓存键必须绑定软件、Profile、授权实例、设备范围和当前生效配置版本；被高层覆盖时低层变化不应改写当前结果，清除覆盖后才刷新到低层版本。

### PolicyVersion

软件授权策略的不可变版本，包含通用授权规则和生效时间。策略更新生成新版本，不覆盖历史版本。激活时写入 `LicenseInstance` 快照，运行时安全撤销、软件停用、最低版本和风控仍可实时判断。

### CapabilityDefinition / Entitlement

`CapabilityDefinition` 定义一个软件可以使用的能力：键名、类型、默认值、范围、是否公开、所属 Profile 和版本。套餐或客户端配置只能引用已登记的定义。

`Entitlement` 是一张卡或一个授权实例实际得到的能力值，例如：

```json
{
  "feature.export": true,
  "limit.projects": 5,
  "edition.name": "pro"
}
```

能力键须使用合法命名空间，例如 `feature.export`；以软件/Profile归属隔离，不同软件可使用同名键，Software A 的值不能覆盖 Software B。

### 平台侧 SoftwareAdapter

平台侧适配器是代码中的小模块，不是数据库里可执行的脚本。默认适配器负责通用在线授权；特殊适配器只能通过注册表按 `adapter_key + adapter_version` 选择，不允许在核心服务里堆积：

```python
if software_id == "skinforge":
    ...
```

适配器只拥有四类职责：

1. 校验产品特有的、已登记的请求上下文；
2. 将通用策略映射成客户端可理解的能力；
3. 返回标准授权决定，不直接改余额、卡密或审计；
4. 提供自己的契约夹具和负向测试。

它不能决定卡密是否存在、到期时间、下游归属、额度扣除或撤销优先级；这些仍归通用核心。

## 运行时选择顺序

```text
请求
  → 校验 software_id / profile_id / client_id / target / arch / channel
  → 解析 SoftwareProfile
  → 加载 PolicyVersion、CapabilityDefinition 和 PlanSnapshot
  → 选择 adapter_key + adapter_version
  → 通用安全与状态校验
  → 适配器做有限产品校验
  → 统一返回 authorization.v1
  → 写审计和请求证据
```

任一身份组合不匹配都拒绝，不能“猜一个相近软件继续执行”。适配器异常只能返回结构化错误，不能部分扣额度、创建孤立授权或写入成功审计。

## 新增软件的标准流程

1. 管理端新建：名称必填，服务端生成稳定 ID、默认 stable Profile/client_id 和生效策略，首个套餐可选，默认不开放任何下游。
2. 在对应软件行下载 software-bind.v2。软件侧无需管理员权限，不再请求平台 AI 重新登记或回填 ID。
3. 将 `软件授权接入包/` 复制到软件项目，与对应软件后台下载的 JSON 一起交给软件侧 AI。先核对语言框架、真实入口、模板版本/哈希和协议映射；使用包内准备工具，再从唯一09指令实施。平台维护的包内模板是现行通用源，不能拿退休外部母版覆盖。
4. 现行桌面模板已包含卡密页、真实五动作 HTTP/proof、完整JSON验签、心跳/续期和本地签名合同。软件侧配置真实构建版本、稳定硬件身份、设备安全存储与核心入口，落实自己的核心合同校验、所有受保护入口和失效停用；具体产品若需不同UI/能力，由自己的副本适配并验证。
5. 需要特殊能力时只登记当前软件的命名空间能力；通用接入不改平台核心。旧入口替换要有本软件基线和回归证据。
6. 首轮用隔离夹具验证；正式站接入测试只用既有 test_downstream_b 的 test_only/0 成本卡。按 00/09 验单机、错卡、到期、撤销、断网、补时间、空值和更新；双机挤机缺条件就记录未验证。
7. 软件项目保存对接结果及配置 SHA-256、模板来源、软件版本和证据。平台对象 active 只表示接口可用，不等于客户端已接通；不得用状态变更代替实机验收。

协议身份不变的 UI/普通业务迭代不重新登记；改授权动作、字段语义、设备证明或身份时，重新核对三方合同。

## “不影响其他软件”的机器验收

每新增一个软件必须自动生成以下检查：

- A 的策略、套餐和能力不能出现在 B 的目录、卡密或客户端响应中。
- A 的 Profile 与 B 的 Profile 使用相同 `client_id` 时仍不能互相激活。
- A 的适配器故障不能改变 B 的余额、授权、会话或审计。
- A 的策略新版本不改变已经生成卡密的 PlanSnapshot 和 LicenseInstance。
- 归档 A 不会归档 B；停用 A 只影响 A 的新业务和 A 的客户端策略。
- 客户端伪造 `software_id`、`profile_id`、`downstream_id`、`expires_at` 或能力值时，服务端按数据库事实拒绝或忽略。
- 同一 API 版本的未知能力字段必须安全忽略或按合同拒绝，不能改变核心状态。
- 核心 EXE 的静态配置、网络调用和运行时日志中不能出现中央平台地址或平台主密钥；平台请求只能由对应授权 A 发起。
- 软件 A 的授权 A 不能读取软件 B 的本地缓存、LocalBroker 或授权结果；空的联系方式/购买链接必须让 A 和核心隐藏对应 UI 区域。
- A 的配置版本变化或授权撤销必须按合同刷新/失效缓存，不能依靠旧缓存永久放行。

### 失败处理

```
配置错误 / 身份冲突 → 不发布 Profile
适配器不支持 → 返回 ADAPTER_UNSUPPORTED，不改数据
客户端版本过低 → VERSION_BLOCKED，不撤销无关软件
运行时风控或撤销 → 只影响对应授权对象
```

## 文档、代码和测试的分工

| 层 | 负责什么 | 不能代替什么 |
|---|---|---|
| PROJECT / ADR | 产品边界和不可逆决定 | 不能代替运行时权限 |
| API / Schema | 字段、版本、错误和兼容性 | 不能代替数据库约束 |
| Profile / Policy / Capability | 软件差异的声明式配置 | 不能存放任意可执行逻辑 |
| 平台 Adapter Registry | 少量真正特殊的服务端实现 | 不能变成按软件堆 if/else |
| 软件授权 A / LocalBroker | 平台到核心之间的产品接入和本地稳定合同 | 不能把平台密钥、任意脚本或跨软件缓存交给核心 |
| 测试和 Feature Guard | 证明旧软件仍未受影响 | 不能掩盖未执行的真实链路 |
| 审计和发布状态 | 追溯谁何时改变了哪个软件 | 不能恢复已删除的秘密 |

因此，“加新软件不影响其他软件”不是一句文档承诺，而是一个必须由代码、约束、隔离测试和发布门共同证明的结果。

## 零基础界面约束

管理端新增软件使用单表单：`填写名称 → 创建 → 下载本软件 JSON`；规则预填可改，套餐可稍后添加。默认页面只显示普通中文和常用字段；原始 JSON、Adapter Key 和协议细节放在“高级信息”只读区，不要求用户手填。

不同软件的参数必须显示在当前软件上下文内，页面顶部始终显示“软件 / Profile / 通道”。切换软件时清空旧筛选并重新加载，防止把 A 的数据误操作到 B。
