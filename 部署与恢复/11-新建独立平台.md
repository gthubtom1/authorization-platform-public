# 新建一套独立授权平台（不是恢复旧平台）

这份文档只适用于：从公开 GitHub 源码新建一个完全独立的授权平台。换 VPS、恢复现有客户、保留旧卡密/设备/授权时，必须改读 [05-密钥永远一套](05-密钥永远一套.md)、[07-只有这个文件夹够不够](07-只有这个文件夹够不够.md) 和 [08-完整部署SOP](08-完整部署SOP.md)，不能使用本文件生成新密钥替代旧密钥。

公开仓库已经包含业务逻辑和依赖：Django 服务、数据库模型和迁移、管理员/下游账号、软件/Profile/套餐、额度、卡密生成与加密、激活/验证、设备绑定、授权签名、发布验签、对象存储、Docker Compose、Nginx 和安装器。公开仓库不包含任何真实密钥，这是正确的；新平台的密钥由本地工具一次生成并保存到受保护目录。

## 生成密钥

在已审核的源码 checkout 中运行，`--domain` 必须是已经确认并准备接 DNS 的真实域名，`--candidate-commit` 是准备部署的 Git 提交：

```bash
python3 scripts/generate-fresh-platform-secrets.py \
  --output-dir /opt/authorization-platform-fresh-secrets \
  --bundle-output /media/recovery-usb/authorization-platform-recovery-kit.enc \
  --bundle-password-file /var/lib/authorization-platform-private/recovery-kit-password.txt \
  --domain auth-new.example.net \
  --candidate-commit "$(git rev-parse HEAD)"
```

工具会生成：

- `production.env`：Django、邀请/额度卡/授权 HMAC、卡密加密、授权签名和发布验签配置；
- `postgres.env`：全新 PostgreSQL 用户密码；
- `object-store.env` 与 `object-store-init.env`：全新对象存储管理员和应用用户；
- `compose.env`：当前锁定的容器镜像摘要；
- `release-signing-private.pem`：发布签名私钥，通常只留在受控的发布机器，不放到运行服务器；
- `README.txt`：这套新平台材料的边界和拷贝说明；
- `authorization-platform-recovery-kit.enc`：可放到 U 盘或离线存储的加密灾备包，包含上述稳定密钥材料和文字说明，不包含包密码。

`--bundle-password-file` 只用于无人值守生成示例；包密码必须放在密码管理器或另一份密封记录中，不能和 `.enc` 放在同一个 U 盘目录。若不想使用文件传密码，可以省略两个 bundle 参数，先生成目录，再用 `scripts/recovery_kit.py pack` 交互输入密码：

```bash
python3 scripts/recovery_kit.py pack \
  --source-dir /opt/authorization-platform-fresh-secrets \
  --output /media/recovery-usb/authorization-platform-recovery-kit.enc
```

工具拒绝覆盖已有目录或灾备包，不读取旧钥匙包，不读取旧数据库，也不会打印任何秘密。生成目录可以在确认灾备包可解密后删除；公开 Git、软件接入包和聊天中都不能出现这些文件。

## 安装空平台

把前五个 env 文件分别复制到新服务器代码树的 `deploy/`：

```text
deploy/production.env
deploy/postgres.env
deploy/object-store.env
deploy/object-store-init.env
deploy/compose.env

/media/recovery-usb/authorization-platform-recovery-kit.enc
```

随后只运行完整安装器：

```bash
cd /opt/authorization-platform
AUTH_DOMAIN=auth-new.example.net bash deploy/install-site.sh
```

必须看到 `VERIFY_OK`。安装器会安装主机依赖、创建对象存储内部 TLS、启动 PostgreSQL/MinIO/应用、执行迁移、创建空平台第一位管理员、接入 Nginx 和维护服务。它不会生成平台卡密/授权密钥，也不会替你打开备份总开关。

空平台的第一位管理员随机口令会写入 root-only 文件。首次登录后立即改成负责人保管的口令。新平台的管理员、下游、软件、套餐、额度和卡密都从空库开始，之后按管理端流程创建；卡密生成与加密逻辑已经在代码中，不需要把真实卡密写入仓库。

## 发布签名

`release-signing-private.pem` 只用于受控发布机：

```bash
python3 scripts/build_release_manifest.py \
  --version v1.0.0 \
  --key /secure/release-signing-private.pem \
  --key-id "production.env 中的 RELEASE_SIGNING_KEY_ID"
```

运行平台只保存 `RELEASE_SIGNING_PUBLIC_KEY`。发布私钥和平台授权签名私钥用途不同，不能互换，也不能复用 `DJANGO_SECRET_KEY`。

## 首次验收

先在目标服务器上完成：

1. `VERIFY_ONLY=1` 再跑一遍安装器并确认仍是 `VERIFY_OK`；
2. 检查管理端、下游登录、`/healthz/` 和根路径 404；
3. 创建一个测试软件、测试 Profile、测试套餐和受控测试下游；
4. 用测试卡验证激活、设备绑定、verify、到期和撤销流程；
5. 用 `scripts/release_candidate_acceptance.py` 检查生产环境变量的独立性；
6. 保存这套新平台的加密灾备包、数据库备份、对象存储备份和提交哈希。

灾备包保存的是稳定的身份和密钥；数据库 `.enc`、对象存储文件和最新恢复证明是会变化的业务数据。为了让一只 U 盘承担恢复职责，可以在 U 盘建立以下目录，并按周期更新最新数据备份：

```text
authorization-platform-recovery/
├─ authorization-platform-recovery-kit.enc
├─ database/
│  └─ latest-database.enc
├─ object-storage/
│  └─ latest-object-manifest.json
└─ README.txt
```

恢复时先用单独保存的包密码执行 `scripts/recovery_kit.py unpack`，再把恢复出的五个 env 放回 `deploy/`；随后按 [08-完整部署SOP](08-完整部署SOP.md) 安装空平台，最后在隔离目标恢复数据库和对象存储。不要把数据库备份硬编码进公开源码。

这套平台以后更新时继续使用同一目录内的密钥，不要再次运行本工具。再次运行会生成另一套信任根，不能解密旧卡密，也不能让旧客户端继续信任原平台。

## 明确边界

- 新建独立平台：可以用本工具生成一套新的密钥和空账本。
- 现有平台换机/恢复：不能用本工具；必须携带原 env、原数据库、原对象存储和原 `installation_id`。
- 公开 GitHub：包含代码、迁移、卡密和授权业务逻辑、依赖模板与本 SOP，但永远不包含真实秘密。
- 生产数据：不在源码仓库内，必须由负责人使用私有密钥/备份渠道注入。
